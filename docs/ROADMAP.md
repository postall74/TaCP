# Дорожная карта разработки

## Правила чтения

Порядок сверху вниз — приоритет. Задача готова только при выполнении всех её
критериев приёмки. «Владелец» отвечает за результат, но не обязан в одиночку
писать код других областей: он передаёт им зафиксированный контракт или запрос.

| Статус | Значение |
|---|---|
| `ready` | объём, владелец, критерии и зависимости определены |
| `blocked` | требуется решение из `DECISIONS.md` или внешний доступ |
| `in progress` | агент работает в своей ветке |
| `review` | есть PR и приложен результат проверки |
| `done` | принято PM и выполнен Definition of Done |

## Релизная цель R1 — стабильный совместный контур

Цель R1: новый агент может взять одну задачу, локально воспроизвести проверки и
доставить изменение без случайного изменения контракта или чужого модуля.

### P0 — сначала восстановить достоверную базу

| ID | Задача и результат | Владелец | Зависит от | Критерии приёмки |
|---|---|---|---|---|
| CORE-001 | Исправить frontend typecheck: корректно использовать общие `Input`/`Select` и устранить необъявленный `loadUsers` | Frontend | — | `npm run typecheck` проходит после чистой установки; исправленное создание/редактирование пользователя вручную проверено в светлой и тёмной темах |
| CORE-002 | Сделать Node-проверки воспроизводимыми | QA | CORE-001 | В новом чистом checkout `npm ci`, `npm run typecheck`, `npm test`, `npm run build` запускаются документированными командами; нет зависимости от ручного запуска файлов из `node_modules` |
| CORE-003 | Убрать дублирующий CI и артефакты сборки из Git-цикла | QA | CORE-002 | Один обязательный workflow запускает typecheck, unit tests и build обоих слоёв; `.gitignore` покрывает `**/bin/`, `**/obj/`, `dist/`, `node_modules/`; план очистки ранее отслеживаемых артефактов согласован, не выполнен молча |
| CORE-004 | Опубликовать контрактную дисциплину | PM | — | Приняты `AGENTS.md`, документы ролей, формат handoff и первый реестр контрактов; команда может стартовать без устных инструкций |
| CORE-005 | Подготовить production-конфигурацию без секретов в репозитории | Backend | ADR-006 | Шаблон переменных/секретов, безопасные development defaults и инструкция запуска разделены; demo-учётные данные не считаются production-настройкой |

CORE-001, CORE-002 и CORE-003 — блокеры любого продуктового merge. CORE-004
можно выполнить параллельно с ними. CORE-005 не блокирует локальную разработку,
но блокирует любой внешний релиз.

### P2 — после R1 и P1-срезов

- История цен и парсеры прайсов: только после источника данных, частоты
  обновления, юридических ограничений и стратегии ошибок.
- Согласование ТКП, комментарии, подписи и уведомления: после модели доступа
  ADR-002 и аудита.
- Нормативные проверки шин, УЗО и заземления: после ADR-004; результат должен
  содержать источник/версию нормы и не подменять инженерную экспертизу.
- Производственная эксплуатация: TLS, бэкапы, наблюдаемость, rate limiting и
  аудит — после ADR-006.

## Контрактный реестр

| Версия | Назначение | Статус | Публикует | Потребляют |
|---|---|---|---|---|
| `core-v1` | Проекты, каталог, auth, роли — существующий контур | needs-audit | Backend | Frontend, QA |
| `cabinet-v1` | Физическая модель шкафа и конфигуратор | planned | Backend | Frontend, QA |
| `time-v1` | Сессии работы и отчётность | blocked: ADR-005 | Backend | Frontend, QA |
| `status-v1` | Переходы статусов и причина проигрыша | blocked: ADR-001 | Backend | Frontend, QA |

`needs-audit` означает: API уже есть, но его клиентский контракт, авторизация и
сквозные тесты должны быть сверены до следующего расширения.

## Минимальный план одного среза

```text
PM: критерии + version + ADR ───────────────┐
Backend: OpenAPI/DTO + migration + fixture ─┼─> integration handoff
Frontend: UI против fixture ────────────────┤
QA: test cases против fixture ──────────────┘
                                            ↓
                                API + UI + tests + docs accepted
```

Это не последовательная очередь: после публикации fixture frontend и QA идут
параллельно с backend. Единственная синхронизация — короткий контрактный handoff
и итоговый интеграционный PR.

## Definition of Done

Для любой задачи:

1. Выполнены все критерии её строки и не изменена несогласованная область.
2. Пройдены команды роли; приложен их фактический вывод или ссылка на CI.
3. Есть тест для новой детерминированной логики либо обосновано, почему сценарий
проверяется только вручную.
4. Обновлены контракт, миграция, `CURRENT_STATE.md` или `DECISIONS.md`, если
изменение затрагивает соответствующий артефакт.
5. PR описывает поведение, границы и способ проверки; PM подтверждает, что
задача не дублирует незавершённую работу другого агента.
