# Дорожная карта разработки

## Правила чтения

CORE-006 (PM, процесс; HTTP без изменений): экономный контекст, единственный
владелец commit/push — PM, QA по событиям. Критерии: согласованы AGENTS,
TEAM_PROTOCOL и четыре роли; QA automation удалена; PM automation обновлена;
правила доставлены трём агентам; документация проверена и опубликована.
Основание — прямое поручение пользователя 2026-09-23. Старые указания на
самостоятельные commit/push агентов и регулярный опрос QA отменены.

Порядок сверху вниз — приоритет. Задача готова только при выполнении всех её
критериев приёмки. «Владелец» отвечает за результат, но не обязан в одиночку
писать код других областей: он передаёт им зафиксированный контракт или запрос.

| Статус | Значение |
|---|---|
| `ready` | объём, владелец, критерии и зависимости определены |
| `blocked` | требуется решение из `DECISIONS.md` или внешний доступ |
| `in progress` | агент работает в своей ветке |
| `review` | есть PR и приложен результат проверки |
| `done` | принято PM и выполнен Definition of Done |

доставить изменение без случайного изменения контракта или чужого модуля.

## Версии новых контрактов

### SEC-002 — совместимость экрана входа с auth-v2

Владелец: Frontend. Статус: ready, после CORE-001; версия: auth-v2 / ADR-008.
Подтверждённый аудитом дефект: LoginGate предлагает анонимную регистрацию в
серверном режиме, которая будет отклоняться auth-v2. Область: LoginGate и
необходимые UI-компоненты; client DTO и серверные права не менять.

Критерии: серверный режим показывает только вход и сообщение «Для получения
доступа обратитесь к администратору»; переключение local → remote сбрасывает
режим регистрации; локальное demo-поведение сохранено; административное
создание пользователя сохраняет JWT текущего admin. Проверки роли и ручной
сценарий обеих тем обязательны. Реальный API smoke — после backend fixture и
SEC-001, до него handoff считается частичным. QA владеет регрессионными тестами.
Rollback: возврат UI commit допустим только до включения auth-v2 на сервере.

### CATALOG-001 — исправить обновление существующей позиции каталога

Владелец: Backend. Статус: `ready`. Приоритет: P1. Контракт:
`catalog-write-v1`; обратно совместимое исправление существующего PUT, без
изменения DTO, URL, ролей и миграций.

Подтверждённый trigger на `main` `1edff933`: после создания позиции корректный
`PUT /api/catalog/{id}` с JWT роли engineer возвращает 500, потому что EF
отслеживает найденную `Equipment` и затем пытается присоединить второй экземпляр
с тем же ключом через `Update`. Последующий GET сохраняет прежние значения.
Контрольный PUT неизвестного id успешно создаёт позицию.

Область ограничена соответствующим обработчиком в `backend/TkpApi/Program.cs`.
Для существующей позиции входные значения переносятся в уже отслеживаемую
сущность; id берётся из URL. Сохраняются Staff policy, текущая upsert-ветка для
неизвестного id и обработка tombstone. Новые правила уникальности, валидации,
frontend-изменения и миграции не входят.

Приёмка: существующая позиция обновляется с 200 и GET подтверждает все значения;
повторный PUT того же id идемпотентен; неизвестный id сохраняет текущую upsert-
семантику; проверены 401 и разрешённые Staff-роли; tombstone-сценарий не
регрессирует. Проходят backend tests и Release build. QA независимо повторяет
HTTP-сценарии на изолированной БД. Исправление не закрывает RATE/OPS gate.

### AUTH-TYPES-001 — синхронизировать TypeScript-типы с auth-v2

Владелец: Frontend. Статус: `ready` после WIZ-UI-001. Приоритет: P2.
Контракт `auth-v2` и HTTP wire format не меняются; backend и миграции не входят.

Подтверждённый аудитом разрыв: login возвращает `expiresAt` как Unix milliseconds
`number`, а `src/api/client.ts` объявляет `string`; register возвращает краткий
объект `{id,email,fullName,role}`, но клиент объявляет полный `AuthUser`.
`backend/TkpApi/auth-v2.fixture.json` уже точно отражает фактические ответы.
Текущие вызовы не читают `expiresAt`, а после register перезагружают список
пользователей, поэтому пользовательский runtime-дефект не заявляется.

Область: типы ответа login/register в `src/api/client.ts`; QA-owned контрактный
тест отдельно. Ввести отдельный тип ответа регистрации, сохранить `AuthUser` для
`login.user`, `/auth/me` и `/auth/users`, не синтезировать отсутствующие поля.
Приёмка: типы совпадают с fixture и фактическим JSON; login→me и admin
register→users работают; проходят frontend typecheck/tests/build и независимая
QA-проверка fixture/runtime shape. Изменение обратно совместимо на HTTP.

Реализация `aff32110`, независимый QA `e93828d8`; проверенное поведение включено
в `main` `1edff933`, повторная реализация и повторный QA не требуются.
Область: LoginGate/UI; тесты принадлежат QA. При переходе remote → local

числом. Отдельная ветка и commit; rollback — возврат UI commit.

### ADMIN-001 — отдельная оболочка административной панели

Владелец: Frontend. Статус: `ready`. Приоритет: P1. Контракт:
`admin-shell-v1` / ADR-010. NEED-001: `partial`.

Область: `src/**`, кроме тестов; HTTP DTO, `src/api/client.ts`, backend,
миграции и права не менять. Вынести существующие административные экраны из
основного layout подготовки ТКП в отдельный маршрут/layout. Ссылка и прямой
доступ доступны только admin; manager/engineer не видят ссылку и не получают
административный экран. Сохранить существующие сценарии пользователей,
справочника и удалённых позиций, локальный demo-режим и обе темы.

Приёмка: `npm run typecheck`, frontend tests и build проходят; ручной сценарий
admin/manager/engineer проверен в обеих темах; переходы не теряют JWT текущего
admin; основной интерфейс ТКП не содержит административных форм. Независимый QA
проверяет навигацию, прямой URL, сохранение существующих операций и регрессию
основного интерфейса. Статистика и недостающие API-операции не входят в этот
срез и не считаются закрытием NEED-001.

### ADMIN-002 — восстановление позиции из корзины справочника

Владелец: Backend. Статус: `ready`. Приоритет: P1. Контракт:
`catalog-recycle-v1` / ADR-011. NEED-001: `partial`.

Реализовать уже вызываемый клиентом `POST /api/catalog/{id}/restore` без
изменения DTO и миграций. Только admin может восстановить сохранённый снимок из
`deleted_equipment` в активный каталог; manager/engineer получают 403,
анонимный запрос — 401. Успех возвращает 204. Повтор для уже восстановленной
позиции идемпотентен; неизвестный ID — 404. Конфликт ID или SKU с другой
активной позицией — 409 без частичного изменения данных.

Приёмка: backend unit/integration tests и Release build; QA проверяет
delete→deleted→restore, повтор, unknown ID, ID/SKU conflict, 401/403, сохранение
всех полей и отсутствие частичной записи при ошибке. Область backend и его
тестовый контракт; frontend не менять. Задача не закрывает NEED-001 целиком.

### ADMIN-003 — удаление пользователя администратором

Владельцы: Backend и Frontend в разделённых областях. Статус: `ready`.
Приоритет: P1. Контракт: `user-admin-v1` / ADR-012. NEED-001: `partial`.

Подтверждённый разрыв: административная страница показывает кнопку удаления,
но вместо API выводит сообщение «функция в разработке». Backend публикует
`DELETE /api/auth/users/{id}` с политикой AdminOnly: успешное удаление — 204,
неизвестный ID — 404, попытка удалить текущего пользователя или последнего
оставшегося admin — 409 без изменений. Удаление другого admin допустимо, если
после операции остаётся хотя бы один admin. Схема БД и остальные auth DTO не
меняются; проекты сейчас не имеют ссылки на AppUser, каскадные изменения не
добавляются.

Frontend добавляет типизированный client/store вызов и заменяет заглушку на
реальное действие с подтверждением, состоянием выполнения и обновлением списка.
Кнопка удаления текущего пользователя остаётся недоступной; 404/409 показываются
понятным сообщением, JWT текущего администратора не теряется.

Приёмка: Backend проверяет 401/403, 204, 404, self-delete 409, last-admin 409 и
удаление одного из нескольких admin без побочных изменений; Frontend — обе темы,
отмену подтверждения, успех и ошибки. QA независимо повторяет HTTP/UI-сценарии,
typecheck/tests/build обоих слоёв проходят. Изменение остаётся отдельной веткой;
само по себе не закрывает NEED-001 и не разрешает merge/tag.

### ADMIN-004 — атомарная защита роли последнего администратора

Владелец: Backend. Статус: `blocked` до handoff ADMIN-003. Приоритет: P1.
Контракт: `user-admin-v2` / ADR-013. NEED-001: `partial`.

Подтверждённый аудитом риск: существующий
`PUT /api/auth/users/{id}/role` считает администраторов до отдельных операций
снятия и назначения роли. Параллельные запросы могут принять решение по одному
устаревшему состоянию. После ADMIN-003 все способы удаления пользователя или
снятия роли admin должны использовать общую транзакционную сериализацию и не
оставлять систему без администратора.

Публичные request/response DTO и успешные статусы существующего PUT сохраняются.
Попытка снять роль у последнего admin возвращает 409 без изменения ролей;
параллельные role-change/delete дают не более одного допустимого успеха и после
завершения оставляют минимум одного admin. QA проверяет последовательные и
конкурентные сценарии в PostgreSQL. Frontend в этот срез не входит.

## Минимальный план одного среза

```text
PM: критерии + version + ADR ───────────────┐
Backend: OpenAPI/DTO + migration + fixture ─┼─> integration handoff
Frontend: UI против fixture ────────────────┤
QA: test cases против fixture ──────────────┘
                                            ↓
                                API + UI + tests + docs accepted
```

Это не последовательная очередь: после публикации fixture frontend и QA идут
параллельно с backend. Единственная синхронизация — короткий контрактный handoff
и итоговый интеграционный PR.

## Definition of Done

Для любой задачи:

1. Выполнены все критерии её строки и не изменена несогласованная область.
2. Пройдены команды роли; приложен их фактический вывод или ссылка на CI.
3. Есть тест для новой детерминированной логики либо обосновано, почему сценарий
проверяется только вручную.
4. Обновлены контракт, миграция, `CURRENT_STATE.md` или `DECISIONS.md`, если
изменение затрагивает соответствующий артефакт.
5. PR описывает поведение, границы и способ проверки; PM подтверждает, что
задача не дублирует незавершённую работу другого агента.
