### Статус ADR-003 и ADR-004 после нормативного исследования

Дата: 2026-09-28. Статус обоих решений: `proposed`, не приняты.

`research/normative/` принят как черновой пакет `normative-research-v1`, а не
как нормативный контракт или доказательство соответствия. Владелец проверки
источников — инженерный эксперт; PM отвечает за область задачи, версии и запись
решения. QA проверяет прослеживаемость fixtures после публикации контракта, но
не подменяет инженерную или юридическую экспертизу.

ADR-004 можно принять только после NORM-001: проверки полных первичных текстов,
точных пунктов, таблиц, исключений и поправок, применимых перечней ТР,
переходных положений и договорных требований. Официальные карточки подтверждают
ввод ГОСТ IEC 61439-1/-2-2024 с 01.04.2026, но сама замена национального
стандарта не доказывает универсальный запрет старой редакции для всех процедур.
ПУЭ пока представлены картой глав, а применимость IEC 60204-1 требует отдельной
проверки. Электрообогрев и специальные промышленные условия исследованы не
полностью.

ADR-003 можно принять только после утверждения классификации изделия и
минимальных исходных данных. Модель должна разделять IP оболочки и сборки,
расчётную нагрузку и сумму номиналов аппаратов, ориентировочный тепловой подбор
и проверку конструкции, кнопку останова и safety-функцию. Ссылки на 8.4.2/8.4.3
и ограничение двух корпусов считаются неподтверждёнными до NORM-001.

## ADR-006a — минимальная безопасная конфигурация

Дата: 2026-09-22. Статус: accepted. Владелец: PM.

CORE-005 разрешён до выбора хоста: контракт `runtime-config-v1`, HTTP DTO не
меняются. Вне Development обязательны явно заданные DB connection, JWT key,
issuer/audience, разрешённые origins/hosts. При отсутствующих или demo-секретах
запуск завершается понятной ошибкой без вывода значения. Swagger по умолчанию
выключен вне Development, CORS ограничен allowlist. Bootstrap администратора
только явно включённой настройкой с внешними credentials, без demo fallback.
Backend публикует точные имена параметров и шаблон без секретов; QA проверяет
отказ на плохой конфигурации и успешный запуск с валидной.
Это breaking change конфигурации production, но не HTTP. Development сохраняет
документированный локальный путь запуска. Полный ADR-006 (хост, TLS, backup,
RPO/RTO) остаётся открытым и блокирует внешний выпуск.

## ADR-007 — отдельное пространство данных

Дата: 2026-09-22. Статус: accepted. Владелец: PM по поручению пользователя.

Tenant соответствует компании или личному пространству. Первая целевая модель:
отдельный контейнерный стек и БД на tenant, общие хост и versioned images.
Разделяются также токены, credentials, storage и backups. Подробности и gates:
[DEPLOYMENT_PLAN](DEPLOYMENT_PLAN.md). TEN-001 публикует `tenant-deploy-v1` до
изменения контрактной границы. Существующие данные остаются в одном исходном
tenant; автоматическое распределение данных между компаниями запрещено без
отдельного плана миграции. ADR-002 по правам внутри компании остаётся открытым.

## ADR-008 — регистрация только администратором

Дата: 2026-09-22. Статус: accepted. Владелец: PM.

SEC-001, `auth-v2`: POST `/api/auth/register` доступен только авторизованному
admin; аноним получает 401, manager/engineer — 403, без создания пользователя.
Admin сохраняет действующий request/response и выбор роли; ошибки валидации 400.
Login остаётся анонимным. Backend проверяет отсутствие AllowAnonymous,
перекрывающего policy, на защищённом endpoint; bootstrap — по ADR-006a.
Это намеренное несовместимое усиление прав core-v1; UI управления пользователями
должен передавать JWT администратора. QA проверяет негативные HTTP-сценарии и
положительный сценарий admin, frontend подтверждает совместимость клиента.
Точный fixture публикует backend перед исполнением тестов. Изменений схемы БД
не ожидается; backend обязан подтвердить это в handoff.

## ADR-009 — ставки сохраняются в БД tenant

Дата: 2026-09-29. Статус: accepted. Владелец: PM.

`RATE-001`, контракт `rates-persistence-v1`: существующие маршруты
`GET /api/rates` и `PUT /api/rates`, JSON DTO и политики `Staff`/`AdminOnly`
сохраняются. Единственный актуальный набор ставок хранится в PostgreSQL каждого
tenant, поэтому перезапуск API не возвращает значения по умолчанию и разные
tenant не разделяют ставки. Новая БД получает текущие значения по умолчанию:
Design 1800, Production 1800, Software 2200, Smr 1800, Pnr 1800.

Изменение требует versioned EF migration и rollback-инструкции. Миграция не
меняет расчётные формулы, округление, права или другие данные. PUT сохраняет
полный существующий DTO атомарно; дополнительные правила диапазонов не вводятся
без отдельного продуктового решения. До независимой проверки default, update,
restart и изоляции двух БД restart gate OPS-001 остаётся незакрытым.

## ADR-010 — отдельная оболочка административного интерфейса

Дата: 2026-09-30. Статус: accepted. Владелец: PM по прямому требованию
пользователя.

`ADMIN-001`, контракт `admin-shell-v1`: административные функции выводятся из
основной оболочки подготовки ТКП в отдельный маршрут и layout. Ссылка и прямой
доступ разрешены только роли admin; UI-проверка не заменяет серверные политики.
На первом срезе переносятся только уже существующие пользовательские и
каталожные действия, включая существующее представление удалённых позиций.
HTTP DTO, `src/api/client.ts`, backend-модели, миграции и права не меняются.

Статистика по направлениям и производителям, недостающие операции обновления и
полное управление корзиной требуют следующих versioned API-срезов. Поэтому
ADMIN-001 даёт только `partial` для NEED-001 и сам по себе не разрешает merge в
`main`, версионный тег или объявление потребности закрытой.
