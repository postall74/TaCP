# CAB-001 / ADR-003 — предложение для решения

Статус: проект решения, не контракт. Дата: 2026-10-18.

## Что есть сейчас

`Cabinet` в TypeScript и C# хранит строковый `kind`, имя, позиции со снимками
цены, трудозатраты, секции, форму разделения и пользовательский эскиз дверцы.
Явных габаритов, серии, способа монтажа, условий среды и двух различных IP
пока нет. Эскиз дверцы содержит относительные координаты и не даёт размеров.

Владелец продукта уточнил 2026-10-18, что «общий вид» NEED-012 должен быть
техническим чертежом. Поэтому DOOR-004 становится потребителем физической
модели шкафа. Нельзя переводить относительные координаты эскиза в миллиметры
по догадке или называть их нормативным чертежом.

## Предлагаемая граница cabinet-v1

1. Сохранять существующие поля и идентификаторы без переосмысления. Добавить
   отдельную классификацию изделия, габариты, серию/модель оболочки, способ
   монтажа, условия среды и *раздельные* IP оболочки и готовой сборки.
2. Для старых шкафов новые поля остаются `unknown`/`null`; миграция не выводит
   их из `kind`, имени, секций или эскиза. Неизвестное не равно «проверено».
3. Данные расчётной нагрузки и номиналы аппаратов хранить отдельно. Тепловой
   подбор отмечать как предварительный до появления исходных потерь, условий
   охлаждения и подтверждённого метода. Кнопка останова сама по себе не
   означает подтверждённую safety-функцию.
4. Сервер публикует версию DTO, примеры JSON, правила 400/403/409, миграцию и
   поведение старого клиента при полном PUT. Frontend и QA работают только по
   этому handoff. Старые снимки версий не переписывать молча.

## Что должен утвердить владелец продукта с инженерным экспертом

- Классы изделий первой версии и обязательные поля для каждого класса.
- Какие данные может вводить инженер как оценочные, а какие требуют документа
  или подтверждения изготовителя.
- Допустимые значения монтажа/условий среды и единицы габаритов.

До утверждения этих пунктов ADR-003 остаётся `proposed`, а CAB-001 и зависимые
CAB-002/WIZ-001 не получают API-реализацию. Нормативные правила и заявление о
соответствии отдельно зависят от ADR-004 и проверки первичных источников.

## Результат подготовительных handoff Frontend и Backend

Проверена интеграционная база `71af6bfa` без изменения файлов. Сейчас серверный
полный PUT проекта удаляет и заново создаёт граф шкафов; лишь `doorLayout` явно
сохраняется по `Cabinet.id`, когда поле отсутствует. Старый клиент отправляет
полный проект также после восстановления версии и отложенной синхронизации.
Поэтому простое nullable-поле новой спецификации будет стираться при старом PUT.

Контракт должен до реализации определить отдельную семантику **отсутствующего**
поля, явного `null` и переданного значения для уже существующего `Cabinet.id`.
Техническое предложение Backend: отсутствующее поле сохраняет сохранённый блок,
явная очистка задаётся отдельно; неподдерживаемая будущая версия читается без
потерь, но её разрушительная замена отклоняется до записи. Для этого потребуется
отдельный DTO или отслеживание присутствия JSON-поля: текущее связывание прямо
в EF entity не различает omission и `null`. Это предложение, не принятый wire
contract.

Старые version snapshots остаются как были. Требует решения, означает ли
восстановление такого снимка «физические поля неизвестны» или сохранение
текущих данных шкафа; молчаливое обогащение снимка исключено. Откат на старый
сервер при разрешённом полном PUT может стереть новые данные, поэтому нужен
совместимый rollback build либо остановка записи и восстановление из backup.

Frontend выявил, что Wizard собирает размеры, монтаж, IP-фильтр и корпус, но
переносит их в итоговый Cabinet главным образом через `name`/`items`; чертёж
извлекает размеры из названия и подставляет условные значения. После принятия
контракта эти экраны должны получать явные поля, а при их отсутствии показывать
`unknown`/предварительный результат без выдуманных физических значений.

## Подготовительный handoff DOOR-004 (база `f9aec228`, без изменения кода)

Frontend и Backend независимо подтвердили: `doorLayout` хранит центры элементов
в координатах 0..1000 виртуальной области каждой двери, а SVG редактора задаёт
только экранную геометрию. `CabinetDraft` извлекает размеры из названия и
подставляет условные 2000×800×600, IP54 и цоколь 100 мм; его нельзя считать
источником технического чертежа. `DocumentTab` печатает единый HTML как PDF
через браузер и экспортирует тот же HTML в Word; отдельного чертёжного листа,
разрыва страниц и проверенного SVG-вывода в Word пока нет.

Для размерного листа расположения центров минимально нужны явные миллиметровые
габариты шкафа и каждого полотна, положение полотен в общем виде и точный
физический прямоугольник, которому соответствуют координаты 0..1000. Начало
координат, направление осей, порядок дверей, единицы/точность, источник и
статус геометрии надо утвердить. Конвертация центров должна быть единой:
`Xмм = offsetXполотна + leftобласти + x/1000 × widthобласти`, аналогично Y.
Округлённые миллиметры не заменяют сохранённые нормализованные координаты.

Владелец продукта 2026-10-18 выбрал для DOOR-004 размерный общий вид с
координатами центров элементов. Чертёж отверстий/вырезов дополнительно требует подтверждённой геометрии
каждого устанавливаемого изделия, включая несколько центров для парных
элементов, ориентацию, посадочные размеры и правила допусков/запретных зон.
Тип `kind` и подпись не дают таких данных. Производственный чертёж исключён
из DOOR-004. Для выбранного размерного вида всё ещё нужны принятый ADR-003 и
точный контракт; нормативное соответствие не заявляется без ADR-004.

Предлагаемое fail-closed поведение: у старого шкафа без `doorLayout` или
подтверждённой физической геометрии доступен лишь неразмерный UI-эскиз;
технический лист не строится и не извлекает размеры из имени/спецификации.
Снимок версии не обогащается текущей геометрией молча. Перед печатью нужен
preflight с указанием неполных шкафов. Для full PUT обязательна семантика
отсутствующего блока, явной очистки и неизвестной будущей схемы, иначе старый
клиент или rollback способны уничтожить геометрию.
