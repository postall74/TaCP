# План CI/CD и изоляции клиентов

Статус: целевая архитектура, 2026-09-22. Реализация и внешний выпуск ещё не приняты.

## Целевая модель

Tenant — отдельная компания либо личное пространство пользователя. Для первой
версии каждому tenant выделяются API, PostgreSQL, отдельный volume, секреты и
сеть в собственном Compose project. Общими остаются хост Docker, reverse proxy,
репозиторий, образы и механизм выпуска. Отдельный hostname ведёт к одному стеку.
Идентификатор из запроса не выбирает БД: API получает единственную строку
подключения из конфигурации своего развёртывания.

Каталог, закупочные цены, тарифы, пользователи, ТКП, экспорты и резервные копии
принадлежат одному tenant. Личное пространство — tenant с одним пользователем;
права сотрудников внутри компании остаются отдельным открытым ADR-002.
Общую библиотеку номенклатуры можно рассмотреть позднее только отдельным ADR.

Для каждого стека нужны отдельные JWT key/issuer/audience, DB credentials,
storage и backup prefix. Токен A не должен приниматься B. БД не публикуется на
внешний порт; reverse proxy имеет доступ к web/API, а не ко всем БД.
Общий хост не даёт изоляции от его администратора или компрометации ядра;
требование отдельных хостов можно принять отдельным решением.

## Этапы и release gates

1. CORE-001/002/003: воспроизводимый checkout, единый CI, обязательные проверки
   PR. CORE-005 и SEC-001 закрывают конфигурацию и регистрацию до внешнего доступа.
2. TEN-001: backend публикует `tenant-deploy-v1`, параметры запуска, совместимость,
   конфигурацию токенов, миграцию существующего экземпляра и fixtures двух tenant.
3. OPS-001: воспроизводимые образы и Compose, постоянные тома, health checks,
   лимиты ресурсов, логирование без секретов, запуск без root где поддерживается.
4. OPS-002: GitHub Actions проверяет PR; доверенный release build публикует
   образы в GHCR, идентифицируемые SHA/digest. Staging и production получают
   тот же digest, секреты не доступны untrusted PR. Параллельные deploy одного
   tenant сериализуются. Настройки GitHub environments проверяются с учётом плана.
5. TEN-002: QA поднимает A/B, проверяет CRUD, импорт/экспорт, поиск, роли и
   токены; прямой доступ к данным B из A запрещён. Перезапуск сохраняет цены.
6. OPS-003: backup перед миграцией, восстановление в отдельном тестовом стеке,
   smoke после deploy, остановка rollout при ошибке. Откат образа допустим только
   при совместимой схеме; иначе применяется проверенный план восстановления БД.

PM принимает каждый gate по конкретному SHA и результатам QA. Сроки хранения
backup, RPO/RTO, домен, ресурсы сервера и доступы ещё требуют эксплуатационных
данных; до этого production deployment остаётся blocked. Секреты вводятся через
защищённое хранилище, не через документацию или сообщения агентов.

## Официальные источники

Проверены 2026-09-22; это основания проектирования, не доказательство реализации.

- [EF Core: multi-tenancy](https://learn.microsoft.com/en-us/ef/core/miscellaneous/multitenancy):
  поддерживается отдельная БД через конфигурацию connection string. Применение:
  TEN-001, один DbContext/экземпляр использует БД своего tenant.
- [Docker Compose в production](https://docs.docker.com/compose/how-tos/production/):
  отдельная конфигурация production и пересоздание контейнеров при обновлении.
  Применение: OPS-001, неизменяемые образы и постоянные данные отдельно.
- [Compose project name](https://docs.docker.com/compose/how-tos/project-name/):
  именование проектов. Применение: уникальные project names каждого tenant;
  само имя не заменяет проверку сетей, credentials и volumes.
- [GitHub deployment environments](https://docs.github.com/en/actions/concepts/workflows-and-actions/deployment-environments):
  правила деплоя и доступ к environment secrets. Применение: OPS-002,
  раздельные staging/production и проверка доступности protection rules.

Перед реализацией владелец сверяет документацию выбранных версий зависимостей.
Изменение архитектуры оформляется ADR, а не переносится из примера автоматически.
