# Протокол работы команды из четырёх агентов

## Роли и их единственная зона решения

| Роль | Решает | Не меняет без контракта/передачи |
|---|---|---|
| Frontend | UX, React-компоненты, состояние, адаптер API | backend-модели, миграции, CI, требования продукта |
| Backend | API, данные, миграции, серверные правила, конфигурация | React UI, frontend-fixtures, критерии продукта |
| QA | тестовые сценарии, test harness, CI, качество релиза | продуктовую семантику и production-код вместо автора |
| PM | приоритет, объём, решения, принятие и документацию | реализацию фич вместо профильного агента |

Разделение не отменяет ревью: каждый агент сообщает об обнаруженной проблеме
владельцу, но не исправляет чужой модуль попутно.

## Режим работы задачи

При параллельной работе каждый агент использует отдельный git worktree.
Переключать ветку в общем E:/dev/TaCP во время работы других агентов нельзя.
PM ведёт [доску состояния](PM_STATUS.md) и [план эксплуатации](DEPLOYMENT_PLAN.md).
QA передаёт дефекты PM и владельцу; владелец передаёт diff, PM возвращает SHA QA.
CI принадлежит QA; PM отвечает за принятие релиза и координацию deployment.

1. PM создаёт строку с ID, владельцем, критериями, зависимостью и при
   необходимости версией контракта.
2. Владелец создаёт ветку `codex/<роль>/<id>-<кратко>`. Один PR — одна задача.
3. Если задача пересекает UI/API/тесты, backend сначала публикует contract
   handoff. После этого frontend и QA работают параллельно с fixture.
4. Агент передаёт краткий handoff: ID, worktree/ветка, base SHA, пути,
   контракт/миграция, команды с итогом, ограничения. Подробности — ссылкой на файл.
5. QA даёт независимый результат. PM сверяет критерии, документацию и отсутствие
   конфликтов, затем принимает PR.
6. PM сверяет результат с `USER_NEEDS.md`. Закрытие исходной потребности требует
   обновлённой пользовательской инструкции со скриншотами; после зелёных QA/CI
   PM сливает в `main` и создаёт аннотированный тег версии с перечнем `NEED-*`.

## Экономия токенов и единый владелец Git

Правила приняты пользователем 2026-09-23, заменяют прежние указания агентам
самостоятельно коммитить и публиковать ветки.

- Commit/push/PR и операции интеграции выполняет только PM. Автор оставляет
  изменения в своём worktree и подтверждает готовность файлов к снимку.
  PM проверяет diff, исключает чужие файлы/секреты/артефакты, коммитит явный
  список путей, публикует без force и сверяет remote SHA. Проверки привязаны
  к содержимому; изменение после проверки требует проверки затронутого сценария.
- Источники читать один раз, затем diff и нужные строки. Исключать зависимости,
  build output и историю разговоров из широких поисков. Независимые чтения
  объединять; вывод ограничивать итогом и первой существенной ошибкой.
- Один отчёт на результат/дефект/блокер; не пересылать прежний отчёт целиком.
  Обычный handoff — до 8 строк плюс ссылка; контракт/сложный дефект может быть
  подробнее. Полные логи хранить локально вне Git, в сообщении — итог и путь.
- Сначала адресная проверка при разработке; обязательный набор роли перед
  handoff выполняется один раз для финального изменения. Повтор — при новом
  коде, исправленной среде или новом провале. Независимый QA не заменять словами
  автора; неизменный результат QA повторно не воспроизводить без причины.
- PM сохраняет 30-минутный контроль через компактные snapshots/cursors.
  При неизменном состоянии не читать историю, не будить агентов и не создавать
  статусные коммиты. Таймера QA нет; PM передаёт ему только новые события.
- Не создавать дополнительных агентов ради мелких задач; не менять модель
  или глубину рассуждений автоматически. Экономия достигается объёмом контекста,
  количеством повторов и точным scope, а не пропуском критериев безопасности.

## Формат contract handoff

```markdown
ID: CAB-001
Версия: cabinet-v1
Владелец: backend
Маршрут и авторизация: POST /api/… — Staff
Request: { ... }
Response: { ... }
Ошибки: 400 — …; 403 — …; 409 — …
Совместимость/миграция: …
Fixture: путь или JSON-блок
Готово для: frontend, QA
```

Без этого формата frontend не блокируется на ожидании API, но и не изобретает
поля. QA пишет сценарии по тем же кодам ошибок и fixture.

## Доска состояния

PM ведёт одну строку на активную задачу в PR/трекере:

| ID | Владелец | Состояние | Версия контракта | Ветка / PR | Следующий handoff |
|---|---|---|---|---|---|
| `CORE-001` | frontend | ready | — | — | typecheck result |

Запрещены две активные задачи, которые редактируют один production-файл. Если
это неизбежно, PM делит работу по подготовительному контракту или назначает
единственного редактора файла.

## Когда остановиться и передать вопрос PM

- Требование меняет права, хранение персональных данных, переходы статусов,
  формулу цены или трактовку ГОСТ/ПУЭ.
- Поле должно быть добавлено в оба слоя, но нет версии контракта.
- Нужны платная зависимость, внешняя система, секрет, production-доступ или
  удаление данных.
- Тест показывает конфликт ожиданий frontend и backend.

PM фиксирует решение в `DECISIONS.md`; после этого задача получает новый
критерий, а не устное исключение.

## Проверки перед передачей

- Frontend: `npm run typecheck`, `npm test`, `npm run build`.
- Backend: `dotnet test backend/TkpApi.Tests`,
  `dotnet build backend/TkpApi/TkpApi.csproj --configuration Release`.
- QA: адресные независимые проверки нового diff/контракта; старые сценарии
  исследовать при провале либо подтверждённой связи с дефектом. Чистая установка
  нужна при изменении зависимостей/среды или проверке воспроизводимости.
  Полный обязательный CI остаётся автоматическим gate; QA разбирает его падения.
- PM: ссылки из README/docs, корректный статус задач, тестовое доказательство в
  PR и отсутствие незарегистрированного решения.

До CORE-002 допустима диагностическая альтернатива `node …/tsc`, но она не
считается постоянной командой команды.
