# Архитектура и контракты

## Карта системы

```text
React UI ──> Zustand store ──> typed REST client ──> ASP.NET Core API ──> PostgreSQL
     │             │                    │                       │
     └── чистые TS-расчёты               └── C# расчётные зеркала ┘
```

Frontend находится в `src/`: `types.ts` — доменная модель, `store.ts` — состояние
и синхронизация, `api/client.ts` — HTTP-граница, `utils/` — чистая логика,
`components/` и `admin/` — UI. Backend находится в `backend/TkpApi/`:
`Program.cs` — маршруты, `Models.cs`/`TkpDbContext.cs` — данные,
`AuthExtensions.cs`/`Rights.cs` — идентификация и права, `Services/` — доменные
сервисы. Автотесты расположены рядом с чистыми TS-модулями и в
`backend/TkpApi.Tests/`.

## Инварианты, которые нельзя нарушать молча

1. В каталоге хранится закупочная цена; продажная цена вычисляется расчётом, а не
   записывается вторым источником.
2. Позиция в шкафу — снимок имени, SKU и закупочной цены на момент добавления.
3. В JSON идентификаторы и enum-значения строковые; даты проекта передаются как
   unix-миллисекунды. Swagger работающего API — оперативная спецификация HTTP.
4. `rates-persistence-v1`: DTO и права `/api/rates` обратно совместимы; один
   набор ставок хранится в БД текущего tenant и не разделяется между БД.
5. UI-проверка прав — подсказка, серверная проверка — обязательна. Изменение
   прав синхронно меняет `src/utils/roles.ts`, `backend/TkpApi/Rights.cs` и их
   тесты.
6. Миграция БД — часть backend-задачи. Изменение модели без проверенной миграции
   не готово к слиянию.
7. Локальный режим — демо/разработка; доступ с реальными пользователями требует
   серверного режима и безопасной конфигурации.
8. `admin-shell-v1`: административный UI имеет отдельные маршрут и layout;
   доступ к нему видит только admin, а серверные политики остаются источником
   фактического разрешения операций.

## Правило контракта для параллельной работы

Каждая cross-layer задача получает версию, например `cabinet-v1`.

1. Backend публикует в задаче: маршрут, метод, request/response JSON, статусы
   ошибок, правила авторизации, миграцию и один пример ответа.
2. PM фиксирует версию в дорожной карте и журнале решений. До принятия версии
   frontend не угадывает поля.
3. Frontend создаёт/обновляет метод в `src/api/client.ts` и разработывает экран
   против checked-in fixture с этим JSON. Он не ждёт запущенную БД.
4. QA пишет контрактные и негативные сценарии по той же версии. После появления
   API fixture заменяется реальным вызовом без изменения продуктовой семантики.
5. Изменение опубликованной версии требует новой версии или явно
   обратно-совместимого поля; PM фиксирует решение до merge.

## Границы текущих сервисов

| Область | Рабочая граница | Состояние |
|---|---|---|
| Проекты, каталог, пользователи | API ↔ `src/api/client.ts` | Интегрировано |
| Расчёт, CSV, права | TS и C# чистые модули | Нужны дифференциальные сценарии |
| Составные шкафы | `utils/kit.ts` и `KitEngine.cs` | Частично интегрировано |
| Секционирование | `utils/segments.ts`, модель и миграции | Проверить сквозной API-сценарий |
| Конфигуратор/тепло/сборки | `backend/TkpApi/Services/` | Прототипы, не подключать в UI без `cabinet-v1` |
| Время, профиль, согласование | UI-идеи и частичные экраны | Требуют продуктового решения и контракта |

## Принятые изменения конфигурации и доступа (ещё не реализованы)

- `runtime-config-v1` / CORE-005 / ADR-006a: HTTP без изменений; production
  configuration несовместима с demo defaults, требуется настройка перед upgrade.
- `auth-v2` / SEC-001 / ADR-008: register становится admin-only (401/403),
  успешные DTO сохраняются; анонимные клиенты регистрации должны перейти на
  административный сценарий. Login сохраняется. Backend публикует fixture.
- `tenant-deploy-v1` / TEN-001 / ADR-007: проектирование отдельной БД и стека
  для каждого tenant; версия пока planned. Существующая БД — один исходный
  tenant, без автоматического перераспределения. Миграция и rollback подлежат
  проверке до принятия реализации. Подробности: [DEPLOYMENT_PLAN](DEPLOYMENT_PLAN.md).

## Источники проектных фактов

- Фактическое поведение: исходники и тесты.
- Публичная HTTP-поверхность: Swagger запущенного API и принятие контракта.
- Приоритет и объём: `ROADMAP.md`.
- Необратимые или спорные решения: `DECISIONS.md`.

## Граница нормативных доказательств

`research/normative/` хранит исследовательские вводные и реестр источников.
Пока ADR-003/004 не приняты, эти материалы не образуют API-контракт и не дают
системе права показывать нормативный `pass`. Версионированное правило должно
хранить источник, редакцию, точную область применения, пункт, входные данные,
результат `pass|fail|not-checked|not-applicable|needs-expert`, ограничения и
доказательство. Отсутствие данных никогда не преобразуется в `pass`, а смена
rule-set не меняет старые снимки проектов молча.

Будущие изменения `src/types.ts`, `backend/TkpApi/Models.cs`, миграций и
`src/api/client.ts` требуют отдельно принятой версии `cabinet-v*` или
`normative-v*`, fixture, migration notes и описания обратной совместимости.

Не копируйте полный перечень эндпоинтов в несколько Markdown-файлов: он быстро
устаревает. В документации храните назначение и правила, а точные DTO закрепляйте
в версии контракта и проверяйте тестом.
