# ТКП·Про — документация

Веб-сервис подготовки технико-коммерческих предложений для компаний, собирающих
**НКУ**, **АСУ ТП** и **системы электрообогрева**. От опросника заказчика — до
документа ТКП с полной экономикой (себестоимость, маржа, рентабельность).

Стек: **React 18 + TypeScript + Vite 6 + Tailwind v4** (фронтенд),
**ASP.NET Core 8 (Minimal API) + EF Core + PostgreSQL** (бэкенд),
Vitest (фронт-тесты), xUnit (бэк-тесты).

---

## 1. Обзор и принципы

1. **Единое расчётное ядро.** Вся экономика считается в чистых функциях
   (`src/utils.ts → calcProject`); UI и документы только отображают результат.
   Зеркало на сервере — `CalcEngine.cs`; общие сценарии покрыты тестами с обеих
   сторон, чтобы две реализации не разъезжались.
2. **Закупочная цена — в справочнике; цена продажи — вычисляется один раз.**
   `закупка × (1 + наценка %)`. Наценка задаётся в проекте, а не в позиции.
3. **Снапшоты, а не ссылки.** Позиции в шкафе хранят копию `name/brand/unit/
   purchase` на момент добавления: изменение прайса не переписывает уже
   отправленные ТКП.
4. **Три слоя прав** (§8): UI → store → сервер. Прямой вызов API не обходит
   матрицу.
5. **Офлайн-первый.** Все мутации сначала попадают в localStorage, затем
   синхронизируются с сервером; при обрыве — копятся в очереди и доотправляются
   при восстановлении (§2.3).

```
  StructureTab.tsx        — дерево шкафов, правка, пометка удалённых позиций

  CabinetConfigurator.tsx — конфигуратор пустых/преднаполненных шкафов (Б.1)

  ui.tsx / icons.tsx      — дизайн-система

  catalog.ts              — справочник (только закупочные цены)
  templates.ts            — стартовые шаблоны шкафов (ГРЩ/АВР/АСУ/Обогрев)
utils/
  utils.ts                — расчётное ядро calcProject, CSV, форматирование
  rules.ts                — движок проверки совместимости
  roles.ts                — матрица прав «роль → действие» (клиент)
  kit.ts                  — составные шкафы (комплекты CQE N / ПРОВЕНТО)
  segments.ts             — секционирование (ГОСТ IEC 61439-2)
  cabinetTemplates.ts     — логика шаблонов шкафов (Б.1)
  excel.ts                — выгрузка .xlsx (шкафы + ИТОГО + Расчёт + Бюджет)
  localAuth.ts            — локальный режим (нет apiBaseUrl)
```

### 2.2. Backend (`backend/TkpApi`)

Minimal API. При старте: EF-миграции **или** `EnsureCreated` (dev), сид
администратора `admin@tkp.local`, раздаётся фронтенд из `dist/`
(`UseStaticFiles` + SPA-fallback `index.html`), поэтому вся команда открывает
один адрес `http://<сервер>:5085`.

- `Program.cs` — эндпоинты + раздача статики.
- `AuthExtensions.cs` — Identity, JWT, `/api/auth/*`, политики ролей.
- `Rights.cs` — серверная матрица прав (зеркало `roles.ts`).
- `CalcEngine.cs`, `CatalogCsv.cs`, `JsonConverters.cs` — расчёт, импорт CSV,
  сериализация дат (unix-мс).

### 2.3. Данные и синхронизация

Мутация → оптимистично в store → UI пересчитывается → дебаунс → `PUT
/api/projects/{id}`. Ошибка сети — тост, данные не теряются. **Офлайн-очередь**
(`outbox`) сохраняет проекты/справочник, сделанные без связи, и доотправляет их
при восстановлении (heartbeat 45 c, клик по индикатору, гидратация). При пустом
`apiBaseUrl` фронтенд сам проверяет `/api/health` на текущем origin
(`autoDetectApi`) — бесшовный запуск в локальной сети.

## 3. Модель данных (PostgreSQL)

| Таблица | Содержимое |
|---|---|
| `projects` | ТКП: клиент, направление, статус, вся экономика |
| `project_cabinets` | шкафы: вид, часы (сборка/проект/ПО) |
| `project_items` | позиции: **снапшот** `Name/Brand/Unit/Purchase`, `Qty` |
| `project_versions` | снимки версий (`snapshot` jsonb) |
| `equipment` | справочник (закупочные цены) |
| `deleted_equipment` | «корзина» справочника — 90 дней, затем безвозвратно |
| `company_settings` | реквизиты компании **по учётной записи** |
| `rate_cards` | тарифы чел·часов |
| `AspNet*` | Identity: пользователи/роли |

## 4. Модель цен (единая)

- В справочнике — **только закупочная**. Продажа = `закупка × (1 + наценка %)`.
- Работы = часы × ставки тарифов (сборка/проект/ППО), в продаже — с наценкой
  `workMarkup`.
- Себестоимость: оборудование + ТЗР % + сторонние + ФОТ + доп. затраты +
  непредвиденные % + командировки + СМР + ПНР.
- Итог: `оборудование + работы + доставка + СМР/ПНР → скидка % → НДС %`.
- Отчётность: прибыль, рентабельность (`profit/выручка`), наценка к себестоимости.

## 5. Конструктор

### 5.1. Составные шкафы (`utils/kit.ts`)

По образцу ПРОВЕНТО / DKC CQE N корпус комплектуется из узлов (каркас, крыша/
основание, панели, двери, цоколи, траверсы). Ряд «стена к стене»: панели
`ряд+1`, стыки `ряд−1`, цоколи `ряд`; учитываются доп. траверсы.

### 5.2. Секционирование (`utils/segments.ts`, ГОСТ IEC 61439-2)

Функциональные отсеки, перегородки (цена от высоты шкафа), формы разделения
1…4b с автопроверкой требований. Комплект отсеков — в составе шкафа, в документе
и на структурной схеме.

### 5.3. Конфигуратор пустых и преднаполненных шкафов (Б.1)

Шаблон = корпус (пустой) **или** корпус + преднаполнение (несколько АВ на
микроклимат/освещение) + **заказной шифр**. В ТКП вставляется одной строкой с
«Комплект поставки: …»; часы сборщиков учтены в стоимости изделия.

---

## 6. Проверка совместимости (`utils/rules.ts`)

Отходящий автомат ↔ шина по току, УЗИП без вводного АВ, ПЛК без БП 24 В, панель
без ПЛК, греющий кабель без терморегулятора, формы разделения без шинного отсека
— с переходом к шкафу и бейджем на вкладке «Структура».

## 8. Аутентификация и роли

Двухрежимная авторизация: **сервер** (JWT, Identity) и **локально**
(`localAuth.ts`, права администратора — чтобы одиночная разработка не упиралась
во вход). Смена роли действует со следующего входа (JWT несёт роли на момент
логина). Разжаловать последнего администратора нельзя.

### 8.1. Матрица прав (`roles.ts` ⇄ `Rights.cs`)

Применяется в трёх слоях: UI (кнопки гаснут) → store (мутации блокируются) →
**сервер** (`Rights.Can`, отказ 403 + RFC 7807, причина в `detail`).

| Действие | Инженер | Менеджер | Админ |
|---|:-:|:-:|:-:|
| Создание / редактирование / расчёт ТКП | ✅ | ✅ | ✅ |
| Перевод «черновик → на расчёте → отправлено» | ✅ | ✅ | ✅ |
| Решение «выиграно / проиграно» | ❌ | ✅ | ✅ |
| Удаление ТКП | ❌ | ✅ | ✅ |
| Дублирование | ✅ | ✅ | ✅ |
| Справочник: добавление / правка | ✅ | ✅ | ✅ |
| Справочник: удаление / импорт прайсов | ❌ | ✅ | ✅ |
| Реквизиты компании (свои) | ❌ | ✅ | ✅ |
| Тарифы, Пользователи и роли | ❌ | ❌ | ✅ |

## 9. REST API

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/health` | **открытая** проверка доступности |
| POST | `/api/auth/register`, `/api/auth/login` | регистрация / вход |
| GET/POST | `/api/projects` | список / создание |
| GET/PUT/DELETE | `/api/projects/{id}` | чтение / синхронизация / удаление |
| POST | `/api/projects/{id}/cabinets` | пакетное добавление шкафов |
| POST | `/api/projects/{id}/versions?label=` | снимок версии |
| GET/POST | `/api/catalog`, `POST /api/catalog/import` | справочник / CSV-импорт |
| PUT/DELETE | `/api/catalog/{id}` | обновить / удалить (в «корзину» 90 дней) |
| GET | `/api/catalog/deleted` | «корзина» справочника |
| GET/PUT | `/api/rates`, `/api/settings` | тарифы / реквизиты (по аккаунту) |
| GET/PUT | `/api/auth/users`, `/api/auth/users/{id}/role` | пользователи (админ) |

## 12. Дорожная карта

**Сделано:** JWT+роли, двухрежимная авторизация, матрица прав (3 слоя),
офлайн-очередь, «корзина» справочника (90 дней), реквизиты по аккаунту,
онлайн-режим в локальной сети (автодетекция), составные шкафы, секционирование,
**А.3 УЗИП** (все классы + резервный автомат + перенос слаботочных в ПЛК),
**А.4 интерактивный макет дверцы**, **А.6 Работы и ППО** (единообразный вид +
живой расчёт), **Б.1 конфигуратор пустых/преднаполненных шкафов**.

**Осталось** (по направлениям):

**А. Конструктор и мастер подбора**
1. **А.1 «Корпус»** — выбор типа (напольный/навесной), габариты из БД
   (а не хардкод; если нет — ближайший или ручной ввод), составной ряд
   «стенка к стенке» как отдельный шаг **до** габаритов (разные корпуса одной
   глубины), доп. траверсы и устанавливаемое оборудование (по каталогу ПРОВЕНТО).
2. **А.2 «Ввод и линии»** — переименовать и переделать: вводной автомат
   (номинал/полюса, согласование со схемой АВР, межсекционный выключатель),
   отходящие вручную (АВ/АВДТ/УЗО: полюса, номинал, количество + аксессуары),
   учёт (счётчики из БД, где ставить, ТТ поканально), заземление (шины PE/N по
   ГОСТ/ПУЭ).
3. **А.3 УЗИП** — доработка: резервный АВ уже есть; добавить классы УЗИП из БД
   (не только I/II/I+II), слаботочные — в ПЛК (сделано).
4. **А.5 «Приборы»** → «Измерительные приборы»: WB-XXX, ТТ (для обогрева —
   измерение тока поканально на каждую фазу), амперметры/вольтметры на ввод и
   отходящие, ровный вид.

**Б. Шкафы**
5. **Б.2** — система соединения/объединения шкафов: не только «бок к боку», но и
   «передняя дверь к задней» (не более 2 шкафов); найти ГОСТы/ТУ и учесть.
6. **Б.3** — общий вид шкафа по ГОСТ для включения в ТКП + шкафные сборки.

**В. Аналитика и расчёты**
7. **В.1** — расчёт тепловыделений оборудования для подбора микроклимата
   (климатип установки, место установки; предупреждения: нужен обогреватель
   такой-то мощности / мало вентиляторов / нужен кондиционер).

**Г. Отчётность**
8. **Г.1** — выгрузка по направлениям (НКУ/АСУ/Обогрев): малая и большая
   статистика.
9. **Г.2** — выгрузка по производителям (сколько и какого оборудования
   закладывается в ТКП — для поставщиков).

**Д. Администрирование**
10. **Д.1** — отдельная админ-панель (вне основного интерфейса): управление
    пользователями (CRUD), справочником (добавление/удаление/обновление +
    «корзина» удаляемых позиций).
11. **Д.2** — регистрация времени, затраченного на подготовку ТКП (видно только
    администратору).

**Прочее**
12. Парсеры прайсов (rosek24.ru разделы 141/58, streamer.ru и аналоги) —
    автоимпорт номенклатуры и цен.
13. Серверный PDF (QuestPDF) с фирменным бланком.
14. История цен поставщиков и прайсы с датами действия.
15. Расширение правил: селективность, уставки УЗО, сечение шин по току.
16. Код-сплиттинг фронтенда (бандл > 500 кБ — `manualChunks`).
