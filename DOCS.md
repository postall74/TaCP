# Документация проекта ТКП·Про

Версия документа соответствует состоянию `main` после веток
`feature/auth-jwt-roles`, `refactor/pricing-model`, `fix/db-schema-auth-wiring`,
`fix/frontend-build-entry`, `feature/composite-cabinets` (см. §13, журнал изменений).

---

## 1. Обзор и принципы

ТКП·Про — система подготовки технико-коммерческих предложений по трём направлениям:
**НКУ**, **АСУ ТП / АСУ Э**, **системы электрообогрева**.

Ключевые принципы архитектуры:

1. **Бизнес-логика — чистые модули, не зависящие от платформы.** Расчётное ядро
   (`src/utils.ts::calcProject`), правила совместимости (`src/utils/rules.ts`),
   разбор прайсов (`utils.parseCatalogCsv` / `CatalogCsv.cs`) и серверный расчёт
   (`CalcEngine.cs`) не знают ни про React, ни про HTTP. Их можно перенести в
   десктоп (Avalonia/MAUI) и мобильные клиенты без переписывания.
2. **Единая модель цен**: в справочнике хранится только **закупочная** цена;
   наценка применяется **один раз** при расчёте.
3. **Один источник правды для сумм**: и интерфейс, и документ, и Excel-выгрузка
   считают через `calcProject` / `CalcEngine` — цифры не расходятся.
4. **Двухрежимное хранилище**: локально (localStorage) или против C#-бэкенда —
   компоненты разницы не видят.
5. **Конфигурация отделена от кода**: категории, направления, типы шкафов, ставки,
   реквизиты — данные, а не код. Под нового заказчика меняются справочники.

## 2. Архитектура

### 2.1. Frontend (React 18 + TS + Vite 6 + Tailwind v4)

```
src/
├─ main.tsx, App.tsx          — точка входа; оболочка: сайдбар, маршруты, тема, JWT-гейт
├─ store.ts                   — zustand + persist: проекты, каталог, настройки, auth;
│                               двухрежимная синхронизация с бэкендом (дебаунс 700 мс)
├─ api/client.ts              — типизированный REST-клиент (метод на эндпоинт),
│                               JWT-токен в localStorage, заголовок Authorization
├─ types.ts                   — доменная модель (зеркало backend/Models.cs)
├─ utils.ts                   — расчётное ядро calcProject, CSV, форматирование
├─ utils/rules.ts             — движок проверки совместимости (чистые функции)
├─ utils/kit.ts               — конфигуратор составных шкафов (комплекты CQE / CQE N)
├─ utils/excel.ts             — выгрузка .xlsx (SheetJS): шкафы + ИТОГО + Расчёт + Бюджет
├─ data/catalog.ts            — стартовый справочник (~80 поз.) + таблица токов CURRENT
├─ data/templates.ts          — типовые шаблоны ТКП (ЩР, АВР, АСУ, обогрев)
└─ components/                — Dashboard, Editor (вкладки), StructureTab (+Wizard,
                                панель проверок), DocumentTab, CatalogPage, RatesPage,
                                LoginGate, ui.tsx (примитивы), icons.tsx (SVG)
```

**Жизненный цикл данных.** Мутация → оптимистично в store → UI пересчитывается
(`calcProject`) → дебаунс 700 мс → `PUT /api/projects/{id}`. Ошибка сети — тост,
данные не теряются (локальная копия). При старте с заданным `apiBaseUrl`:
`initAuth()` (профиль по токену) + `hydrateFromApi()` (проекты/каталог/тарифы/реквизиты).

### 2.2. Backend (`backend/TkpApi`, ASP.NET Core 8)

```
Program.cs         — Minimal API: эндпоинты, Swagger (+Bearer Authorize), сид каталога
Models.cs          — доменная модель (строковые Id — совпадают с фронтом без конверсий)
```

нет файлов миграций → `EnsureCreated()` (dev); БД уже заполнена, но журнала нет →
**baseline** (миграции помечаются применёнными, данные не пересоздаются); иначе →
`Migrate()`. Команды генерации и отката — в `backend/MIGRATIONS.md`.

## 4. Модель цен и формулы расчёта

**Единственная цена справочника — закупочная (`purchase`).** Цена продажи
вычисляется один раз: `sell_unit = purchase × (1 + Markup/100)`.

Шкаф:
```
eqBase      = Σ purchase × qty                     (база наценки = закупочная)
markupSum   = eqBase × Markup/100
laborCost   = Hours×Rate.Production + DesignHours×Rate.Design + SoftwareHours×Rate.Software
laborSell   = laborCost × (1 + WorkMarkup/100)
cabinetSell = eqBase + markupSum + laborSell
```

Проект:
```
Себестоимость = eqCost + ТЗР%(от eqCost) + ThirdParty + laborCost + ExtraCosts
              → + UnforeseenPct% → + TripCosts + SmrCost + PnrCost
Продажа       = Σ cabinetSell + SmrSell + PnrSell + TransportPct%(от eqBase)
              → − Discount% → + VatRate%  =  ИТОГО к оплате
Profit        = afterDiscount − totalCost
MarginPct     = Profit / afterDiscount × 100     (рентабельность продаж)
MarkupPct     = Profit / totalCost × 100         (наценка к себестоимости)
```

Ставки чел·часов по ролям (design / production / software / smr / pnr) — на странице
«Тарифы», хранятся в `settings.rates` (на сервере — `GET/PUT /api/rates`).

## 5. Мастер подбора (опросник)

`components/Wizard.tsx`, 11 шагов; результат — готовые шкафы (`addCabinetsBulk`).

1. **Корпус**: тип установки, требуемый IP. В каталоге ищутся корпуса с нужным IP;
   если нет — честно «такого нет» + ближайшие (IP67→IP65→IP54) + **ручной ввод**
   (позиция попадает в справочник). «Корпус не нужен» — шаг пропускается.
2. **Ввод/линии**: вводной автомат, отходящие 1P/3P (кол-во + номинал), УЗО,
   учёт (счётчик + ТТ).
3. **АВР**: на БАВР (комплект) / на контакторах с мехблокировкой / реверсивный
   рубильник; линии управления (промежуточные реле).
4. **УЗИП**: тип 2 или 1+2 (подсказка по СП 256).
5. **Кнопки/лампы/переключатели**, «Аварийный стоп».
6. **Шины по току нагрузки**: ≤63 А — гребёнки; ≤160 А — медь 25×3 + 4 держателя;
   ≤250 А — 40×4 + 6; выше — с пометкой о проверке.
7. **Компоновка**: «стена к стене» → боковых панелей = ряд+1 (не 2×ряд); цоколи
   для напольных.
8. **ПЛК**: DI/DO/AI/AO + резерв % → `⌈сигналы/каналы × (1+резерв)⌉` модулей,
   БП 24 В, HMI.
9. **Работы**: часы сборка/проектирование/ППО (× тарифы) + «работы отдельной
   строкой в ТКП».
10. **ЗИП**: % от оборудования, **минимум 1 шт на позицию**, отдельный шкаф «ЗИП».
11. **Сводка**: проверка состава и применение.

### 5.1. Составные шкафы — конфигуратор комплектов (`src/utils/kit.ts`)

По образцу PROVENTO и конфигуратора DKC CQE / CQE N корпус комплектуется не
одной позицией, а **набором узлов** с пересчётом под ряд «стена к стене».
Шаг «Корпус» мастера даёт три режима: **готовый из справочника / составной
комплект / ручной ввод**.

| Система | Монтаж | IP | Сетка габаритов, мм | Состав комплекта |
|---|---|---|---|---|
| **CQE** | напольный | 54 | В 1800–2200 × Ш 600–1200 × Г 400–800 | каркас (4 стойки), крыша, основание, 2 траверсы, боковые и монтажная панели, двери (1–2), цоколи |
| **CQE N** | навесной | 66 | В 400–1000 × Ш 300–800 × Г 150–300 | корпус (рама + задняя стенка), боковые и монтажная панели, 1 дверь |

Ключевые правила комплектования:

- **«Стена к стене»**: на ряд из N шкафов — **N+1 боковых панелей** (вместо
  2×N) и **N−1 стыковых комплектов**; цоколи — по числу шкафов ряда. Пересчёт
  происходит автоматически, когда на шаге «Компоновка» включается ряд или
  цоколи — в состав не дублируются «одиночные» панели и цоколи.
- **Цены** — закупочные таблицы по типоразмеру (негабарит округляется к
  ближайшему). Позиции попадают в шкаф **снапшотами** (как справочные и ручные),
  поэтому смена прайса не переписывает уже отправленные ТКП.
- **Часы сборки** (`kitAssemblyHours`) растут с габаритом, длиной ряда и
  цоколями — выводятся как ориентир для шага «Работы».
- Системы и цены — **данные** (`KIT_SYSTEMS`): новый бренд/серия добавляется
  без правки UI и расчётов. Модуль чистый (без React/HTTP) — при переносе на
  сервер зеркалируется в `KitEngine.cs` без изменения контракта (§11).

## 6. Проверка совместимости (`src/utils/rules.ts`)

| Правило | Уровень | Суть |
|---|---|---|
| Автомат ↔ шина | Ошибка | отходящий АВ/УЗО/рубильник мощнее шины (вводной — самый мощный — исключён, чтобы не было ложных срабатываний на гребёнках отходящих групп) |
| Много АВ без шины | Подсказка | 3+ автоматов без гребёнки |
| УЗИП без вводного АВ | Внимание | УЗИП нельзя безопасно отключить |
| ПЛК без БП 24 В | Внимание | контроллер/модули питаются от 24 В |
| Панель без ПЛК | Внимание | HMI есть, контроллера нет во всём проекте |
| Греющий кабель без терморегулятора | Внимание | кабель будет греть постоянно |
| Пустой шкаф | Подсказка | оборудование не добавлено |

Каждое правило — чистая функция `(шкаф|проект, контекст) → Issue[]`. Контекст несёт
справочник (у `LineItem`-снимка нет категории/тока — карточка берётся по `eqId`) и
проект (для межшкафных правил). Номинальные токи — `Equipment.ratedCurrent`,
таблица `CURRENT` в `data/catalog.ts`. UI: панель «Проверка совместимости» с
переходом к шкафу, бейдж на вкладке, тост при добавлении конфликтной позиции.
При переносе на сервер правила уезжают в `RulesService.cs` с тем же контрактом.

## 8. Авторизация и роли

**Вход обязателен всегда** — пока нет профиля, приложение показывает экран входа
(`LoginGate`). Механика зависит от режима:

- **Серверный режим** (`apiBaseUrl` задан): ASP.NET Identity (`AppUser`: ФИО,
  должность) + JWT (`Jwt:Key/Issuer/Audience/ExpireMinutes` в appsettings).
  Эндпоинты `/api/auth/register|login|me|users`. При старте создаются роли и
  администратор из `Admin:Email/Password` (идемпотентно). Токен в
  `localStorage["tkp-jwt"]`, каждый запрос несёт `Authorization: Bearer …`.
- **Локальный режим** (без бэкенда): пользователи и роли — в
  `localStorage["tkp-users"]` (`src/utils/localAuth.ts`, пароли — SHA-256-хэши).
  Администратор `admin@tkp.local / Admin#12345` создаётся при первом запуске.
  Это полноценная замена для разработки и демо; для боевой эксплуатации —
  только серверный режим (bcrypt, lockout, политики паролей — в Identity).
- `store.ts` переключает режимы в одной точке (`apiBaseUrl`): действия
  `login/register/logout/initAuth/listUsers/setUserRole` одинаковы для UI.
- **Роли**: `admin` (всё + пользователи), `manager`, `engineer` (политика `Staff`).
- **Эндпоинты данных закрыты**: `/api/projects*`, `/api/cabinets*`,
  `/api/catalog*`, `GET /api/rates`, `GET /api/settings` — `Staff`;
  `PUT /api/rates`, `PUT /api/settings`, `/api/auth/users*` — `AdminOnly`.
  Фронтенд грузит данные только после входа (эффект `apiBase && user`).
- Проекты получают `OwnerId` из токена — задел на разделение данных по пользователям.

### 8.1. Матрица прав (`src/utils/roles.ts`)

Единый источник правды «роль → действие»; применяется в двух слоях:
**UI** (кнопки гаснут с подсказкой-`title`) и **store** (мутации
`deleteProject`/`setStatus` блокируются с тостом и возвращают `false`).
На сервере тонкие правила закрывает `PUT /api/auth/users/{id}/role`
(только `AdminOnly`); смена роли действует **со следующего входа**
(текущий JWT несёт прежние роли).

| Действие | Инженер | Менеджер | Админ |
|---|:-:|:-:|:-:|
| Создание / редактирование / расчёт ТКП | ✅ | ✅ | ✅ |
| Перевод «черновик → на расчёте → отправлено» | ✅ | ✅ | ✅ |
| Решение «выиграно / проиграно» | ❌ | ✅ | ✅ |
| Удаление ТКП | ❌ | ✅ | ✅ |
| Дублирование | ✅ | ✅ | ✅ |
| Справочник (CRUD, импорт прайсов) | ✅ | ✅ | ✅ |
| Тарифы нормо-часов | ❌ | ❌ | ✅ |
| Реквизиты компании | ❌ | ❌ | ✅ |
| Пользователи и роли (страница «Пользователи») | ❌ | ❌ | ✅ |

Локальный режим (нет `apiBaseUrl`, `user = null`) — права администратора,
чтобы单机-разработка не упиралась в экран входа.

### 8.2. Поиск и фильтрация проектов (Dashboard)

Портфель рассчитан на десятки ТКП, поэтому на дашборде — строка поиска
(название, номер, заказчик, контакт), фильтр по направлению, диапазон дат
создания и вкладки статусов («в работе / выполнено / проиграно»). Конвейер:
статус → направление → поиск → даты. Счётчик «показано N из M» и кнопка
«Сбросить» появляются при активных фильтрах; пустое состояние различает
«нет проектов» и «ничего не найдено».

- **Правило тестовых данных**: в хелперах обнуляйте все экономические поля
  (`Markup`, `ТЗР`, `Непредвиденные`, `НДС`…) — у модели ненулевые дефолты, и
  «лишние» проценты ломают ассерты (история с `Calc_DiscountThenVat`).

## 11. Расширяемость и мультиплатформенность

Проект проектируется под коммерциализацию и платформы Web / Desktop / Mobile:

- **Общее ядро на C#** (`Models`, `CalcEngine`, `CatalogCsv`, будущие
  `RulesService` и `KitEngine` — зеркала `utils/rules.ts` и `utils/kit.ts`)
  переиспользуется в десктопе (Avalonia/MAUI) и серверных сценариях;
  фронтенд — тонкий клиент REST API.
