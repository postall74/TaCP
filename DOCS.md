# Документация проекта ТКП·Про

Версия документа соответствует состоянию `main` после веток
`feature/auth-jwt-roles`, `refactor/pricing-model`, `fix/db-schema-auth-wiring`,
`fix/frontend-build-entry`, `feature/composite-cabinets` (см. §13, журнал изменений).

---

## 1. Обзор и принципы

ТКП·Про — система подготовки технико-коммерческих предложений по трём направлениям:
**НКУ**, **АСУ ТП / АСУ Э**, **системы электрообогрева**.

Ключевые принципы архитектуры:

1. **Бизнес-логика — чистые модули, не зависящие от платформы.** Расчётное ядро
   (`src/utils.ts::calcProject`), правила совместимости (`src/utils/rules.ts`),
   разбор прайсов (`utils.parseCatalogCsv` / `CatalogCsv.cs`) и серверный расчёт
   (`CalcEngine.cs`) не знают ни про React, ни про HTTP. Их можно перенести в
   десктоп (Avalonia/MAUI) и мобильные клиенты без переписывания.
2. **Единая модель цен**: в справочнике хранится только **закупочная** цена;
   наценка применяется **один раз** при расчёте.
3. **Один источник правды для сумм**: и интерфейс, и документ, и Excel-выгрузка
   считают через `calcProject` / `CalcEngine` — цифры не расходятся.
4. **Двухрежимное хранилище**: локально (localStorage) или против C#-бэкенда —
   компоненты разницы не видят.
5. **Конфигурация отделена от кода**: категории, направления, типы шкафов, ставки,
   реквизиты — данные, а не код. Под нового заказчика меняются справочники.

## 2. Архитектура

### 2.1. Frontend (React 18 + TS + Vite 6 + Tailwind v4)

```
src/
├─ main.tsx, App.tsx          — точка входа; оболочка: сайдбар, маршруты, тема, JWT-гейт
├─ store.ts                   — zustand + persist: проекты, каталог, настройки, auth;
│                               двухрежимная синхронизация с бэкендом (дебаунс 700 мс)
├─ api/client.ts              — типизированный REST-клиент (метод на эндпоинт),
│                               JWT-токен в localStorage, заголовок Authorization
├─ types.ts                   — доменная модель (зеркало backend/Models.cs)
├─ utils.ts                   — расчётное ядро calcProject, CSV, форматирование
├─ utils/rules.ts             — движок проверки совместимости (чистые функции)
├─ utils/kit.ts               — конфигуратор составных шкафов (комплекты CQE / CQE N)
├─ utils/segments.ts          — секционирование: отсеки, перегородки, формы разделения
├─ utils/excel.ts             — выгрузка .xlsx (SheetJS): шкафы + ИТОГО + Расчёт + Бюджет
├─ data/catalog.ts            — стартовый справочник (~80 поз.) + таблица токов CURRENT
├─ data/templates.ts          — типовые шаблоны ТКП (ЩР, АВР, АСУ, обогрев)
└─ components/                — Dashboard, Editor (вкладки), StructureTab (+Wizard,
                                панель проверок), DocumentTab, CatalogPage, RatesPage,
                                LoginGate, ui.tsx (примитивы), icons.tsx (SVG)
```

**Жизненный цикл данных.** Мутация → оптимистично в store → UI пересчитывается
(`calcProject`) → дебаунс 700 мс → `PUT /api/projects/{id}`. Ошибка сети — тост,
данные не теряются (локальная копия). При старте с заданным `apiBaseUrl`:
`initAuth()` (профиль по токену) + `hydrateFromApi()` (проекты/каталог/тарифы/реквизиты).

**Автодетекция same-origin (запуск в локальной сети).** Бэкенд сам раздаёт
собранный фронтенд из `dist/` (`UseStaticFiles` в `Program.cs`), поэтому все
участники сети открывают один адрес — `http://<сервер>:5085`. Чтобы каждому не
вводить URL вручную, при пустом `apiBaseUrl` фронтенд на старте проверяет
`/api/health` на **текущем origin** (`autoDetectApi()` в `store.ts`): ответил —
автоматически включает онлайн-режим и подставляет origin как `apiBaseUrl`; не
ответил (vite-dev на :3000) — остаётся локальным. Это делает развёртывание «один
сервер — вся команда» бесшовным (подробнее — QUICKSTART §5).

**Свежесть фронтенда по сети.** Порт 5085 отдаёт **сборку** из `dist/`, а не
исходники (те — на :3000), поэтому после правок нужен `npm run build`. Чтобы
браузеры участников не «застревали» на старых версиях: `index.html` и
SPA-fallback отдаются с `Cache-Control: no-store`, а хэшированные ассеты
`/assets/*` — `immutable` на год (новый билд = новые имена файлов). При старте
API логирует дату сборки: «index.html от 14.05 18:30» — по ней видно, не устарел
ли `dist/` (диагностика — QUICKSTART §5.6).

**Офлайн-очередь (`outbox`).** Если связь оборвалась, мутации (создание/правка/
удаление проектов, добавление/удаление позиций справочника) складываются в
персистную очередь, а при восстановлении связи отправляются по порядку
(`flushOutbox()`: проекты — идемпотентно «PUT, при 404 → POST», справочник —
upsert). Очередь запускают heartbeat (каждые 45 с), ручная перепроверка
(клик по индикатору в сайдбаре) и гидратация. «Корзина» справочника
(`deleted_equipment`, 90 дней) позволяет пометить в ТКП позицию, удалённую из
общего справочника, пока пользователь был офлайн (§3).

### 2.2. Backend (`backend/TkpApi`, ASP.NET Core 8)

```
Program.cs         — Minimal API: эндпоинты, Swagger (+Bearer Authorize), сид каталога,
                     раздача фронтенда из dist/ (UseStaticFiles + SPA-fallback),
                     «корзина» справочника (deleted_equipment, чистка через 90 дней)
Models.cs          — доменная модель (строковые Id — совпадают с фронтом без конверсий)
JsonConverters.cs  — UnixMsDateTimeConverter: даты в JSON — unix-мс (контракт фронтенда)
TkpDbContext.cs    — IdentityDbContext<AppUser>: проекты/шкафы/позиции/версии + Identity,
                     company_settings (реквизиты на пользователя), deleted_equipment
AuthExtensions.cs  — весь auth: Identity+JWT, политики AdminOnly/ManagerUp/Staff,
                     /api/auth/* (включая PUT /api/auth/me — свой профиль), сид
Rights.cs          — серверная матрица прав (зеркало roles.ts), отказ 403 + RFC 7807
CatalogCsv.cs      — разбор прайсов: чистые ParseLine/Parse + тонкий Import (в БД)
CalcEngine.cs      — серверное зеркало calcProject (закупочная модель)
seed-catalog.csv   — стартовый справочник, 8 колонок
```

**Контракт JSON.** Идентификаторы — строки (генерирует фронтенд), enum'ы —
строками (`"nku"`, `"draft"` — `JsonStringEnumConverter`), **даты — unix-мс**
(`UnixMsDateTimeConverter` читает число или ISO-строку, пишет число — ровно то,
что хранит `src/types.ts`). До появления конвертера `POST/PUT /api/projects`
отвечали `400`: фронтенд слал `createdAt: 1735689600000`, а `DateTime` из числа
не десериализуется — проект создавался локально, но не долетал до БД.

**Схема БД — через EF-миграции.** При старте `EnsureSchema()` (в `Program.cs`):
нет файлов миграций → `EnsureCreated()` (dev); БД уже заполнена, но журнала нет →
**baseline** (миграции помечаются применёнными, данные не пересоздаются); иначе →
`Migrate()`. Команды генерации и отката — в `backend/MIGRATIONS.md`.

## 4. Модель цен и формулы расчёта

**Единственная цена справочника — закупочная (`purchase`).** Цена продажи
вычисляется один раз: `sell_unit = purchase × (1 + Markup/100)`.

Шкаф:
```
eqBase      = Σ purchase × qty                     (база наценки = закупочная)
markupSum   = eqBase × Markup/100
laborCost   = Hours×Rate.Production + DesignHours×Rate.Design + SoftwareHours×Rate.Software
laborSell   = laborCost × (1 + WorkMarkup/100)
cabinetSell = eqBase + markupSum + laborSell
```

Проект:
```
Себестоимость = eqCost + ТЗР%(от eqCost) + ThirdParty + laborCost + ExtraCosts
              → + UnforeseenPct% → + TripCosts + SmrCost + PnrCost
Продажа       = Σ cabinetSell + SmrSell + PnrSell + TransportPct%(от eqBase)
              → − Discount% → + VatRate%  =  ИТОГО к оплате
Profit        = afterDiscount − totalCost
MarginPct     = Profit / afterDiscount × 100     (рентабельность продаж)
MarkupPct     = Profit / totalCost × 100         (наценка к себестоимости)
```

Ставки чел·часов по ролям (design / production / software / smr / pnr) — на странице
«Тарифы», хранятся в `settings.rates` (на сервере — `GET/PUT /api/rates`).

## 5. Мастер подбора (опросник)

`components/Wizard.tsx`, 11 шагов; результат — готовые шкафы (`addCabinetsBulk`).

1. **Корпус**: тип установки, требуемый IP. В каталоге ищутся корпуса с нужным IP;
   если нет — честно «такого нет» + ближайшие (IP67→IP65→IP54) + **ручной ввод**
   (позиция попадает в справочник). «Корпус не нужен» — шаг пропускается.
2. **Ввод/линии**: вводной автомат, отходящие 1P/3P (кол-во + номинал), УЗО,
   учёт (счётчик + ТТ).
3. **АВР**: на БАВР (комплект) / на контакторах с мехблокировкой / реверсивный
   рубильник; линии управления (промежуточные реле).
4. **УЗИП**: тип 2 или 1+2 (подсказка по СП 256).
5. **Кнопки/лампы/переключатели**, «Аварийный стоп».
6. **Шины по току нагрузки**: ≤63 А — гребёнки; ≤160 А — медь 25×3 + 4 держателя;
   ≤250 А — 40×4 + 6; выше — с пометкой о проверке.
7. **Компоновка**: «стена к стене» → боковых панелей = ряд+1 (не 2×ряд); цоколи
   для напольных.
8. **ПЛК**: DI/DO/AI/AO + резерв % → `⌈сигналы/каналы × (1+резерв)⌉` модулей,
   БП 24 В, HMI.
9. **Работы**: часы сборка/проектирование/ППО (× тарифы) + «работы отдельной
   строкой в ТКП».
10. **ЗИП**: % от оборудования, **минимум 1 шт на позицию**, отдельный шкаф «ЗИП».
11. **Сводка**: проверка состава и применение.

### 5.1. Составные шкафы — конфигуратор комплектов (`src/utils/kit.ts`)

По образцу PROVENTO и конфигуратора DKC CQE / CQE N корпус комплектуется не
одной позицией, а **набором узлов** с пересчётом под ряд «стена к стене».
Шаг «Корпус» мастера даёт три режима: **готовый из справочника / составной
комплект / ручной ввод**.

| Система | Монтаж | IP | Сетка габаритов, мм | Состав комплекта |
|---|---|---|---|---|
| **CQE** | напольный | 54 | В 1800–2200 × Ш 600–1200 × Г 400–800 | каркас (4 стойки), крыша, основание, 2 траверсы, боковые и монтажная панели, двери (1–2), цоколи |
| **CQE N** | навесной | 66 | В 400–1000 × Ш 300–800 × Г 150–300 | корпус (рама + задняя стенка), боковые и монтажная панели, 1 дверь |

Ключевые правила комплектования:

- **«Стена к стене»**: на ряд из N шкафов — **N+1 боковых панелей** (вместо
  2×N) и **N−1 стыковых комплектов**; цоколи — по числу шкафов ряда. Пересчёт
  происходит автоматически, когда на шаге «Компоновка» включается ряд или
  цоколи — в состав не дублируются «одиночные» панели и цоколи.
- **Цены** — закупочные таблицы по типоразмеру (негабарит округляется к
  ближайшему). Позиции попадают в шкаф **снапшотами** (как справочные и ручные),
  поэтому смена прайса не переписывает уже отправленные ТКП.
- **Часы сборки** (`kitAssemblyHours`) растут с габаритом, длиной ряда и
  цоколями — выводятся как ориентир для шага «Работы».
- Системы и цены — **данные** (`KIT_SYSTEMS`): новый бренд/серия добавляется
  без правки UI и расчётов. Модуль чистый (без React/HTTP) — при переносе на
  сервер зеркалируется в `KitEngine.cs` без изменения контракта (§11).

### 5.2. Секционирование внутри шкафов (`src/utils/segments.ts`)

Функциональные отсеки и формы внутреннего разделения по **ГОСТ IEC 61439-2** —
панель «Секционирование» в карточке шкафа (вкладка «Конструктор»).

**Модель.** `Cabinet.segments?: CabinetSegment[]` (тип отсека, название,
перегородки 0–4) и `Cabinet.form?: SeparationForm` («1»…«4b»). Поля опциональны:
старые проекты без секционирования не затрагиваются.

**Экономика — без второго источника сумм.** Отсек сам по себе ничего не стоит;
стоимость несут **перегородки** (параметрическая позиция `ПЕРЕГОРОДКА-ВН`,
цена = 1400 ₽/м × высота шкафа, минимум 400 мм) и **типовые комплекты** по типу
отсека (позиции справочника: DIN-рейки, клеммы, шинодержатели…). Кнопка
«Добавить комплект в состав» кладёт их в `cabinet.items` **снапшотами**
(дедупликация по `eqId`, часы сборки +0,5 ч на перегородку) — дальше всё считает
обычный `calcProject`, цифры в документе и Excel сходятся автоматически.

**Формы разделения** (`FORM_META`): метка, описание, требования — формы 2+
требуют шинный отсек, формы 3+ — минимум два функциональных отсека. Требования
проверяются движком совместимости (§6) — замечания появляются в панели проверок
с переходом к шкафу.

**Документы.** В разделе шкафа (А4) выводится строка «Отсеки: … · форма N»;
в приложении Б (структурная SVG-схема) шкаф с отсеками рисуется выше — с
полосами отсеков и подписью формы; линии связи выравниваются по центрам блоков.

**Бэкенд.** Доменная модель зеркалирована в `Models.cs` (`CabinetSegment`,
`Cabinet.Segments/Form`); пока `[NotMapped]` — персист в таблицу
`cabinet_segments` приедет с EF-миграцией (дорожная карта, п. 1). Фронтенд
хранит отсеки в локальной копии проекта, данные не теряются.

## 6. Проверка совместимости (`src/utils/rules.ts`)

| Правило | Уровень | Суть |
|---|---|---|
| Автомат ↔ шина | Ошибка | отходящий АВ/УЗО/рубильник мощнее шины (вводной — самый мощный — исключён, чтобы не было ложных срабатываний на гребёнках отходящих групп) |
| Много АВ без шины | Подсказка | 3+ автоматов без гребёнки |
| УЗИП без вводного АВ | Внимание | УЗИП нельзя безопасно отключить |
| ПЛК без БП 24 В | Внимание | контроллер/модули питаются от 24 В |
| Панель без ПЛК | Внимание | HMI есть, контроллера нет во всём проекте |
| Греющий кабель без терморегулятора | Внимание | кабель будет греть постоянно |
| Пустой шкаф | Подсказка | оборудование не добавлено |
| Форма разделения без шинного отсека | Внимание | формы 2a…4b требуют отделения шин (§5.2) |
| Форма 3+/4+ с одним отсеком | Внимание | функциональные блоки не отделены друг от друга (§5.2) |

Каждое правило — чистая функция `(шкаф|проект, контекст) → Issue[]`. Контекст несёт
справочник (у `LineItem`-снимка нет категории/тока — карточка берётся по `eqId`) и
проект (для межшкафных правил). Номинальные токи — `Equipment.ratedCurrent`,
таблица `CURRENT` в `data/catalog.ts`. UI: панель «Проверка совместимости» с
переходом к шкафу, бейдж на вкладке, тост при добавлении конфликтной позиции.
При переносе на сервер правила уезжают в `RulesService.cs` с тем же контрактом.

## 8. Авторизация и роли

**Вход обязателен всегда** — пока нет профиля, приложение показывает экран входа
(`LoginGate`). Механика зависит от режима:

- **Серверный режим** (`apiBaseUrl` задан): ASP.NET Identity (`AppUser`: ФИО,
  должность) + JWT (`Jwt:Key/Issuer/Audience/ExpireMinutes` в appsettings).
  Эндпоинты `/api/auth/register|login|me|users`. При старте создаются роли и
  администратор из `Admin:Email/Password` (идемпотентно). Токен в
  `localStorage["tkp-jwt"]`, каждый запрос несёт `Authorization: Bearer …`.
- **Локальный режим** (без бэкенда): пользователи и роли — в
  `localStorage["tkp-users"]` (`src/utils/localAuth.ts`, пароли — SHA-256-хэши).
  Администратор `admin@tkp.local / Admin#12345` создаётся при первом запуске.
  Это полноценная замена для разработки и демо; для боевой эксплуатации —
  только серверный режим (bcrypt, lockout, политики паролей — в Identity).
- `store.ts` переключает режимы в одной точке (`apiBaseUrl`): действия
  `login/register/logout/initAuth/listUsers/setUserRole` одинаковы для UI.
- **Роли**: `admin` (всё + пользователи), `manager`, `engineer` (политика `Staff`).
- **Эндпоинты данных закрыты**: `/api/projects*`, `/api/cabinets*`,
  `/api/catalog*`, `GET /api/rates`, `GET /api/settings` — `Staff`;
  `PUT /api/rates`, `PUT /api/settings`, `/api/auth/users*` — `AdminOnly`.
  Фронтенд грузит данные только после входа (эффект `apiBase && user`).
- Проекты получают `OwnerId` из токена — задел на разделение данных по пользователям.
- **Регистрация** (`POST /api/auth/register`): политика пароля — минимум 6 символов
  и хотя бы одна цифра (Identity: `RequireUppercase/Lowercase = false` — единая с
  локальным режимом `localAuth.ts` и сидом `Admin#12345`). Ошибки валидации
  возвращаются **по-русски** (маппер `RuError` в `AuthExtensions.cs`) и показываются
  в форме как есть: клиент разбирает тело ответа (`errors[]`, `detail` RFC 7807 —
  `errorOf` в `src/api/client.ts`), поэтому вместо безликого «HTTP 400 Bad Request»
  пользователь видит «Пользователь с таким e-mail уже существует» и т. п.
- **Смена роли** (`PUT /api/auth/users/{id}/role`, AdminOnly): действует **со
  следующего входа** (JWT несёт роли, выданные при логине). Разжаловать
  **последнего администратора нельзя** — сервер (`Rights.CanChangeRole`) и
  локальный режим (`localSetUserRole`) отвечают отказом «сначала назначьте
  админом кого-то ещё»; правило покрыто `RightsTests`. Если доступ к
  единственному админу всё же потерян (прямая правка БД в обход API) —
  восстановление SQL-скриптом, см. QUICKSTART §5 («Администратор потерял права»).

### 8.1. Матрица прав (`src/utils/roles.ts` ⇄ `backend/TkpApi/Rights.cs`)

Единый источник правды «роль → действие»; применяется в **трёх слоях**:

1. **UI** — кнопки гаснут с подсказкой-`title` (`can`, `canMoveTo`);
2. **store** — мутации `deleteProject`/`setStatus` блокируются с тостом и
   возвращают `false`;
3. **сервер** (`Rights.cs` — зеркало `roles.ts`) — эндпоинты спрашивают
   `Rights.Can(user, …)` и отвечают **403 + RFC 7807** (причина — в `detail`),
   так что прямой вызов API (curl/Swagger/тонкий клиент) правила не обходит:
   - `DELETE /api/projects/{id}` — `project.delete` (менеджер/админ);
   - `PUT /api/projects/{id}` со сменой статуса — `status.decide` для
     «выиграно/проиграно», `status.workflow` для остальных (`PermForStatus` —
     зеркало `canMoveTo`);
   - `PUT /api/auth/users/{id}/role` — `AdminOnly` (как и было).

Приоритет ролей (`admin > manager > engineer`), деградация неизвестной роли до
инженера и тексты отказов (`DenyReason` ⇄ `denyReason`) синхронизированы;
расхождение ловят `RightsTests.cs` и `roles.test.ts` (одни и те же сценарии).
Смена роли действует **со следующего входа** (текущий JWT несёт прежние роли).

| Действие | Инженер | Менеджер | Админ |
|---|:-:|:-:|:-:|
| Создание / редактирование / расчёт ТКП | ✅ | ✅ | ✅ |
| Перевод «черновик → на расчёте → отправлено» | ✅ | ✅ | ✅ |
| Решение «выиграно / проиграно» | ❌ | ✅ | ✅ |
| Удаление ТКП | ❌ | ✅ | ✅ |
| Дублирование | ✅ | ✅ | ✅ |
| Справочник: добавление / правка позиций | ✅ | ✅ | ✅ |
| Справочник: удаление позиций, импорт прайсов | ❌ | ✅ | ✅ |
| Свой профиль (ФИО, должность, телефон) | ✅ | ✅ | ✅ |
| Реквизиты компании | ❌ | ✅ | ✅ |
| Тарифы нормо-часов | ❌ | ❌ | ✅ |
| Пользователи и роли (страница «Пользователи») | ❌ | ❌ | ✅ |

Детализация справочника (`catalog.add` / `catalog.edit` / `catalog.delete` /
`catalog.import`) защищает общую базу: инженер пополняет и правит позиции, но не
удаляет их и не запускает импорт прайсов (массовая перезапись цен). Добавление
идёт с проверкой на дубль по артикулу и по «название+бренд» — существующая
позиция подсвечивается в таблице, а не создаётся повторно. Реквизиты компании
(`settings.edit`) теперь заполняют **менеджер и админ** (`PUT /api/settings` —
политика `ManagerUp`); телефон в профиле меняет сам пользователь
(`PUT /api/auth/me`, поле `PhoneNumber`).

Локальный режим (нет `apiBaseUrl`, `user = null`) — права администратора,
чтобы одиночная разработка не упиралась в экран входа.

### 8.2. Поиск и фильтрация проектов (Dashboard)

Портфель рассчитан на десятки ТКП, поэтому на дашборде — строка поиска
(название, номер, заказчик, контакт), фильтр по направлению, диапазон дат
создания и вкладки статусов («в работе / выполнено / проиграно»). Конвейер:
статус → направление → поиск → даты. Счётчик «показано N из M» и кнопка
«Сбросить» появляются при активных фильтрах; пустое состояние различает
«нет проектов» и «ничего не найдено».

### Сделано

- **Аутентификация и права**: JWT + роли, двухрежимная авторизация (сервер +

- **Составные шкафы** (§5.1): конфигуратор комплектов CQE N / PROVENTO, ряд

- **Мастер подбора — 14 шагов**: АВР (2/3/5 вводов, 1-ф/3-ф), ввод и линии,
  заземление (TN-S/TN-C-S/TT/IT + контроль изоляции), УЗИП (силовые + RS-485/
  Ethernet/каналы), кнопки и индикация (**интерактивный макет дверцы** — drag&drop,
  подписи), измерительные приборы,
  шинные сборки по току, компоновка, микроклимат, ПЛК (+искрозащита,
  преобразователи), секционирование (опросник форм), работы и ППО, ЗИП, сводка.
- **Онлайн-режим в локальной сети**: автодетекция same-origin, раздача `dist/`,
  офлайн-очередь, «корзина» справочника (90 дней), реквизиты по учётной записи,
  телефон в профиле.

### Осталось — по направлениям

**А. Конструктор и мастер подбора**

1. **Переработка шага «Корпус»** (по замечаниям заказчика): тип шкафа — ручной
   ввод названия наряду со списком; напольный/навесный — навесной только
   цельносварной (не может быть составным); производитель корпусов — **из
   справочника** (или свой), а не зашит в код; габариты — из характеристик в БД;
   сборка «стенка к стенке» — **отдельный шаг до габаритов** (шкафы разных
   габаритов при совпадающей глубине — одна сборка); «доп. траверсы» → всё
   навесное/присоединяемое оборудование (по документации ПРОВЕНТО);
   секционирование — отдельная составная часть мастера; готовые корпуса из
   конфигуратора (Б.1) — сюда; ручной ввод корпуса — оставить.
2. **«Ввод и линии»** (переименовать + переработать): сначала вводной автомат
   (номинал, полюса; при АВР — межсекционный выключатель, число АВ = схеме АВР);
   отходящие линии вручную (АВ/АВДТ/УЗО: полюса, номинал, количество одного
   номинала/типа, **аксессуары** — галочки/выпадающий список, по несколько на
   аппарат); учёт электроэнергии (сколько счётчиков, где — ввод/отходящие,
   трансформаторы тока, выбор счётчика из списка производителей); заземление —
   сверить закладку PE/N шин по ГОСТ/ПУЭ.
3. **УЗИП**: автоматический выключатель для силового УЗИП; все классы (I, II,
   I+II, III/комбинированные), позиции — **из БД** (streamer.ru); слаботочные
   УЗИП (RS-485 / Ethernet / 24 В DC) перенести в шаг «ПЛК».
4. ~~**Кнопки и индикация — интерактивный макет дверцы**~~ — **выполнено**
   (ветка `feature/interactive-door`): ровные строки ввода (`CountRow`), превью —
   **реальная дверца шкафа** (сталь с градиентом, петли, ручка, вент-прорези),
   перетаскивание кнопок/ламп/переключателей/«авар. стоп» (pointer-события,
   координаты в `doorPos`), свои подписи (`doorLabels`), подпись сверху/снизу
   (`doorLabelSide`), сброс раскладки. Позиции сохраняются при смене количества
   (стабильные ключи элементов).
5. **«Измерительные приборы»** (переименовать «Приборы»): измерители параметров
   сети WB-XXX, трансформаторы тока (поканально на фазы отходящих АВ — для
   электрообогрева), вводные и отходящие средства измерения.
6. **Работы и ППО**: единообразный внешний вид (как у «Кнопок и индикации»).

**Б. Шкафы, компоновка, графика**

1. **Конфигуратор пустых и преднаполненных шкафов**: отдельная сущность «шкаф по
   заказному шифру» — пустой корпус ИЛИ преднаполненный (корпус + АВ на
   микроклимат и освещение). Комплект поставки в ТКП: рама с потолочной панелью,
   панели кабельного ввода, монтажные траверсы ×N, дверь, панель задняя, панель
   монтажная, ключ, цоколь, панели боковые. Часы сборки — в стоимости изделия.
   Готовые варианты переиспользуются в мастере подбора (А.1).
2. **Расчёт тепловыделений** для подбора микроклимата: суммарное тепловыделение
   установленного оборудования, климатическое исполнение и место установки;
   предупреждения — «нужен обогреватель ≥ N Вт» / «мало вентиляторов» /
   «требуется кондиционер».
3. **Общий вид шкафа по ГОСТ** (автосхема для ТКП): фронтальный вид с габаритами,
   дверями, цоколем; для шкафных сборок — несколько корпусов на одном чертеже.
4. **Соединение/объединение шкафов**: не только «стенка к стенке», но и «передняя
   дверь к задней стенке» (**не более 2 корпусов** в такой сборке); подобрать и
   учесть ГОСТ/ТУ на соединения.

**В. Аналитика и администрирование**

1. **Отдельная админ-панель** (вне основного интерфейса): пользователи (CRUD),
   справочник (CRUD + корзина удалённых позиций), выгрузка статистики по
   направлениям (НКУ / АСУ ТП / Обогрев) — малая и большая; **статистика по
   производителям** (сколько раз и какое оборудование закладывается в ТКП — для
   переговоров с поставщиками).
2. **Регистрация времени подготовки ТКП** (видит только админ): учёт времени на
   каждое ТКП (старт/стоп в редакторе или по активности).

**Г. Документы и экспорт**

1. **АВР — однолинейная схема + текстовое описание работы** (вставляются в ТКП
   как приложение, отдельный тумблер «нужен/ненужен»).
2. Серверный PDF (QuestPDF) с фирменным бланком.
3. История цен поставщиков и прайсы с датами действия.
4. Согласование ТКП: комментарии, подписи, уведомления.

**Д. Инфраструктура и качество**

1. **Секционирование — персист**: EF-миграция `cabinet_segments` (снятие
   `[NotMapped]` в `Models.cs`, команды — `backend/MIGRATIONS.md`), серверная
   валидация форм разделения. Фронтенд-часть готова (§5.2).
2. **Составные шкафы — серверное зеркало** `KitEngine.cs` (расчёт комплекта для
   тонких клиентов), новые системы/бренды — данными в `KIT_SYSTEMS`.
3. **Парсеры прайсов** (rosek24.ru — разделы 141/58, streamer.ru и аналоги):
   автоимпорт номенклатуры и закупочных цен по расписанию.
4. Расширение правил: селективность, уставки УЗО, сечение шин по току; граф
   допустимых переходов статусов; **проверка расчёта шинных сборок** (шины и
   шинодержатели — п. А «Шинные сборки» замечаний не имеет, нужна верификация).
5. Код-сплиттинг фронтенда (бандл > 500 кБ из-за recharts/xlsx — `manualChunks`
   в `vite.config.js`) — предупреждение сборки, на скорость разработки не влияет.
