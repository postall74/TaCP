# TEN-001 — tenant-deploy-v1

Дата: 2026-09-28. Владелец: Backend. Статус: contract handoff для PM, OPS-001 и QA;
это описание целевого развёртывания, а не реализация Docker или принятие релиза.
Основание: ADR-007 и DEPLOYMENT_PLAN из PM-ветки. База: `b1bb51eb` (auth-v2).

## Граница контракта

Один tenant — компания либо личное пространство — получает один API-процесс,
одну PostgreSQL-инсталляцию с собственной БД, credentials, сетью и томом данных.
Личное пространство отличается числом пользователей, но не новой ролью или DTO.
Один hostname ведёт к одному стеку. Одинаковый versioned image допустим;
живые данные, ключи и пользовательские файлы не разделяются между стеками.

Новых HTTP-маршрутов, request/response DTO, полей TenantId и правил OwnerId нет.
API берёт единственную ConnectionStrings:Tkp из конфигурации процесса. Tenant
не выбирается из URL-параметра, заголовка, JWT claim или тела запроса. Матрица
прав внутри компании остаётся прежней; её изменение требует ADR-002.

Совместимость: HTTP и схема БД не меняются. Новый tenant создаётся пустым;
существующая БД целиком становится одним исходным tenant A. Копировать её в B
или распределять записи по OwnerId автоматически запрещено. Порядок переноса
и остановки при несоответствиях — [MIGRATION_RUNBOOK.md](MIGRATION_RUNBOOK.md).

## Параметры и границы изоляции

| Ресурс | Обязательное правило |
|---|---|
| Compose project | Уникальный project name для A и B; не использовать общие external DB volumes/networks |
| PostgreSQL | Отдельный процесс/контейнер, БД, login role и случайный пароль каждого tenant; нет публичного DB-порта |
| API connection | API A знает только DB A и её credentials; API B — только B |
| JWT | Разные случайные Key, Issuer и Audience; ValidIssuer/ValidAudience/подпись проверяются существующим auth |
| Ingress | Отдельные точные hostname; proxy маршрутизирует hostname к соответствующему API, неизвестный hostname отклоняется |
| Сети | DB A доступна только сервисам A; DB B — только B; общий proxy не подключён к приватным DB-сетям |
| CORS/hosts | AllowedHosts и Cors:AllowedOrigins только своего приложения; wildcard и адрес другого tenant не разрешены |
| Тома | Раздельные постоянные DB volumes; нельзя подключать один PGDATA к двум экземплярам |
| Файлы/backup/logs | Раздельные пространства и ACL; ни один контейнер/пользователь tenant не читает пространство другого |
| Bootstrap | Admin:Enabled только для явно запланированной инициализации; после неё false и credentials удалены из runtime |
| Статические файлы | Общий неизменяемый frontend build допустим как часть image/read-only asset; в нём не должно быть tenant-секретов или пользовательских экспортов |
| Версии | Одинаковый проверенный digest для одинакового релиза; отдельный deployment record и план отката каждого tenant |

Общий Docker-хост и его администратор остаются общей доверенной границей.
Project name сам по себе не обеспечивает сетевую изоляцию: OPS-001 должен
проверить фактические mounts, сети, публикацию портов и правила ingress.

Используются только существующие параметры [runtime-config-v1](../../CONFIGURATION.md):
ConnectionStrings__Tkp, Jwt__Key/Issuer/Audience/ExpireMinutes, AllowedHosts,
Cors__AllowedOrigins__0, Admin__Enabled/Email/Password, Swagger__Enabled, URLS,
DOTNET_ENVIRONMENT, StaticFilesPath. API не загружает `.env`, manifest fixture
или Docker secret files автоматически. OPS-001 определит передачу секретов
процессу; интерфейс `_FILE` этим контрактом не объявляется реализованным.

## Fixtures двух tenant

[tenants.fixture.json](tenants.fixture.json) — декларативный пример для OPS/QA,
не API DTO, appsettings или готовый Compose. В `environment` приведены реальные
имена runtime-параметров; `resources`, `secretReferences` и `qaData` — только
метаданные планирования. Secret references обозначают разные записи будущего
хранилища, но не настраивают provider и не содержат значений.

Перед запуском заменить `<...>` значениями из хранилища, проверить различие
ключей/паролей и связность ресурсов. DB-имена/hostname/пути в примере тестовые;
конкретный production-хост, mounts, Docker/PG major version и backup storage
выбираются в OPS/ADR-006. URLS `:8080` и /app/web — предлагаемый внутренний
layout для последующего image, не подтверждённая текущая упаковка приложения.

`qaData` задаёт разные имена/SKU/цены тестовых записей и один одинаковый email
для проверки двух независимых Identity-хранилищ. Это не payload создания:
QA использует существующие HTTP DTO и генерирует недостающие поля/credentials
по принятому core-v1/auth-v2. Пример не добавляет постоянных тестов или seed.

## Что уже есть и что не доказано

Факты базы b1bb51eb:

- TkpDbContext содержит каталог, проекты/шкафы/позиции/версии, Identity,
  company_settings и deleted_equipment. Эти данные переносятся вместе.
- Program.cs регистрирует один DbContext на connection string. AuthExtensions
  проверяет подпись JWT, issuer, audience, lifetime. CORE-005 проверяет параметры
  отдельного процесса, но не сравнивает конфигурации разных экземпляров.
- `rates` — объект в памяти Program.cs, а не таблица. DB dump не сохраняет тарифы;
  после рестарта они сбрасываются. Это открытый production-gap, не обещание
  сохранности данных: PM должен назначить решение до принятия restart gate.
- При запуске выполняются миграции, EnsureExtraTables, PurgeDeleted и seed
  пустого каталога. Старт restored API не является read-only операцией.
- Frontend persist/outbox и JWT находятся в браузере. Их нет в DB dump;
  новый origin не получает их автоматически. Смешивание tenant в одном origin
  не входит в v1. Очередь старого origin нужно сверить до cutover.
- Серверного хранилища экспортов этот срез не вводит. Файлы пользователя вне БД
  инвентаризируются отдельно; зарезервированные каталоги fixture не заставляют
  текущий backend писать туда. Клиентские экспорты не мигрируются автоматически.

## Проверки будущей реализации (QA / TEN-002)

1. На отдельных БД A/B создать разные каталоги/цены и пользователей с одинаковым
   email, но разными паролями. Успешные login возвращают токены своего экземпляра.
2. JWT A при вызове защищённого `/api/projects` B получает 401, и наоборот;
   плохой host — 400, чужой origin не получает allow-origin. CORS не считать
   заменой серверной авторизации. Login в обоих tenant остаётся anonymous.
3. С валидным токеном B запросить существующий только в A ID проекта через B:
   404, без записи/изменения в A. Списки/поиск/импорт/экспорт не выдают чужие данные.
4. Убедиться на уровне БД/сетей, что credentials и контейнер A не дают доступа к B;
   сверить mounts/volume IDs и отсутствие публичных DB-портов. Даже разные БД
   могут быть ошибочно подключены одинаковым ConnectionStrings — это отдельный тест.
5. Перезапустить A и проверить каталог/покупные цены/пользователей; B не меняется.
   Сохранность тарифов отдельно заблокирована указанным gap.
6. Восстановить backup A в новое изолированное пространство; B не изменяется,
   секреты и JWT не перенесены из A в B. Сверить данные до первого запуска API.
7. Проверить два отдельных browser origins, отсутствие переноса JWT/outbox между
   ними, fresh login после ротации ключей. UI/реальные export-сценарии — область QA/Frontend.

Успех компиляции одного API не доказывает изоляцию двух Docker-стеков. Эти
сценарии являются требованиями к будущим OPS-001/TEN-002, сейчас не выполнены.

## Открытые решения для PM

- Runtime persistence тарифов, отдельно от перемещения БД.
- Обработка legacy БД без корректной __EFMigrationsHistory и расхождений схемы.
- Конкретные host/TLS, доверенный proxy, ingress и Docker/PG versions.
- Хранилище секретов и способ инъекции, backup ACL/encryption/retention/RPO/RTO.
- Учёт legacy browser outbox/local-only данных, пользовательских файлов и тарифов
  при переносе; их потерю или автоматическое перераспределение не разрешать.
- Политика восстановления после новых записей в A: нет автоматического merge
  с исходной БД и нет разрешения потерять эти записи при откате.

Проверка этого handoff: JSON parse, соответствие runtime-имен коду, раздельность
идентификаторов ресурсов/secret refs, локальные ссылки. Production-код не менялся;
результаты базы b1bb51eb (57 tests, Release 0/0) не запускались повторно для Markdown/JSON.
Новых migrations, Docker-команд, DB-переноса и Git mutations автор не выполнял.

Справка: [Compose project names](https://docs.docker.com/compose/how-tos/project-name/).
