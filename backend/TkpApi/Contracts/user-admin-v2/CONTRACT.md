# ADMIN-004 — user-admin-v2

Основание: ADR-013 / PM docs `14fb5ecb3aa848684da50e8420b2b8a685bb87d9`.
База: ADMIN-003 `6f67dbabea73b7860f1dda87439b05fd83f39f88`.
NEED-001 partial. Этот контракт заменяет ограничение смешанной конкуренции
DELETE↔PUT role из user-admin-v1 для обновлённых экземпляров API.

## HTTP и совместимость

Оба маршрута используют прежнюю AdminOnly policy: 401 анонимному запросу,
403 manager/engineer. Публичные модели, роли и миграции не меняются.

`PUT /api/auth/users/{id}/role` принимает прежний `{ "role": "engineer" }`.
200 возвращает прежние id/email/fullName/position/phone/roles. Неизвестный ID —
404. Конфликт последнего admin теперь **409 вместо 400**, с прежним телом
`{ "errors": [причина из Rights.LastAdminDeny] }`. Остальные Identity failures
сохраняют 400/errors; ошибки БД откатывают транзакцию и дают стандартный 500.
Нормализация ролей не меняется: неизвестная роль по прежнему правилу означает
engineer. Сохранение роли admin у единственного admin разрешено. Снятие своей
роли admin разрешено при наличии другого admin; запрет self-delete не изменён.

`DELETE /api/auth/users/{id}` сохраняет контракт v1: 204 без тела, 404 неизвестный
ID, 409 self-delete или последний admin. Проекты/OwnerId и остальные доменные
данные не меняются. Fixture: [fixture.json](fixture.json).

## Общая транзакционная стратегия

Оба маршрута вызывают AdminInvariantTransaction.BeginAsync до загрузки целевого
пользователя и ролей. PostgreSQL-транзакция получает SHARE ROW EXCLUSIVE locks
на AspNetUsers, AspNetRoles, AspNetUserRoles в одном порядке. Другая поддерживаемая
операция ждёт, затем читает актуальное состояние; прежнего решения по счётчику
до lock больше нет. UserManager использует тот же scoped TkpDbContext и транзакцию.
Снятие старых ролей, назначение новой и commit — одна операция, хотя Identity
выполняет несколько SaveChanges. Любой ранний отказ или ошибка откатывает их все.
Ответ об успехе выдаётся только после commit.

При исходном состоянии с минимум одним admin поддерживаемые PUT/DELETE не
снижают их число до нуля. Из двух конкурирующих операций, каждая из которых
убрала бы одного из двух admin, допускается только первая; вторая получает 409.
Блокировка в БД распространяется на разные API-процессы. SELECT других маршрутов
не блокируется, но конкурентные Identity-записи могут ждать; длительные внешние
транзакции увеличивают задержку. Автоматический retry deadlock не добавлен.

Гарантия требует обновить все экземпляры API, которые принимают PUT/DELETE:
смешанный запуск со старым PUT возвращает прежний race. На rollout остановить
старых writers, затем открыть трафик к обновлённым экземплярам. Прямой SQL,
сторонние writers и ремонт уже повреждённого состояния без admin сюда не входят.
Регистрация/seed не снимают роли; их существующий контракт не расширяется.

Ранее выданные JWT не отзываются немедленно и не меняют role claims после смены
роли. Это прежнее поведение; защита числа admin читает БД даже при старом JWT.
Нельзя заявлять завершённый user lifecycle или немедленный запрет всех действий
удалённого/пониженного пользователя по этому срезу.

## Проверки и rollback

QA проверяет PUT↔PUT, PUT↔DELETE и DELETE↔PUT на двух API-процессах с общей БД,
обе очередности получения lock, 401/403/404/409 без записи, успех 200/204,
self/multiple/last admin, ошибку назначения новой роли после удаления старой,
ошибку commit и сохранение всего состояния Identity. Постоянные QA-тесты и UI
не менялись автором; независимый QA/CI остаётся gate.

Новой миграции нет. Откат image возвращает прежний неатомарный PUT и статус 400
для его last-admin отказа. До rollback заморозить изменения пользователей/ролей,
сделать backup и не открывать конкурентные операции на старой версии. Уже
изменённые роли и удалённые пользователи автоматически не восстанавливаются.
Восстановление backup поверх новых записей требует отдельной сверки данных.
NEED-001 остаётся partial до всех UI/QA/инструкций/релизных gates.
