# ADMIN-002 — catalog-recycle-v1

Основание: ADR-011 / PM contract `100964332dbea752e6383c11e49818d5f628dc99`.
NEED-001: partial. Этот API не закрывает административную панель целиком.

## Контракт

`POST /api/catalog/{id}/restore`, только AdminOnly, тело не требуется.
Успех — 204 без тела. Возвращается сохранённый снимок deleted_equipment с прежним
ID: Sku, Name, Brand, Category, Direction, Unit, Purchase, RatedCurrent, Attrs.
DeletedAt/DeletedBy относятся только к корзине и не добавляются в активную модель.
Снимок не нормализуется и не заменяется данными клиента.

Если снимка уже нет, а активная позиция с ID есть, ответ 204 без изменений;
если ID отсутствует в обеих таблицах — 404. Без новой истории/миграции невозможно
различить ранее восстановленную и иную активную позицию без снимка: существование
активного ID является условием идемпотентного ответа. Если снимок есть, любой
активный ID либо активный SKU без учёта регистра даёт 409 без изменений обеих
таблиц. Активная позиция никогда не перезаписывается восстановлением.
401 — анонимный запрос; 403 — manager/engineer. Ошибки БД не выдаются за 204/409:
транзакция откатывается, необработанная ошибка даёт стандартный 500.
Пример снимка и матрица — [fixture.json](fixture.json).

## Атомарность и совместимость

Операция выполняется в PostgreSQL transaction. SHARE ROW EXCLUSIVE lock на
обе таблицы сериализует восстановление с другими изменениями каталога/корзины.
Это защищает и отсутствие SKU: существующий unique index регистрозависим,
одних row locks для регистронезависимой проверки недостаточно. Обычный SELECT
не блокируется этим lock. Конкурирующие записи ждут завершения короткой операции;
большие импорт/долгая транзакция могут увеличить ожидание. При deadlock/cancel/DB
error частичных изменений нет, автоматических повторов и нового error DTO нет.

Снимок переносится и удаляется из корзины одним SaveChanges в общей транзакции,
204 возвращается после Commit. При ранних 404/409/идемпотентном 204 dispose
транзакции освобождает блокировки без записи. Публичные модели, схема/миграции,
остальные endpoints и права не менялись. Реализован уже существующий frontend
вызов; правок frontend не требуется. Очистка корзины через 90 дней остаётся прежней.

## Rollback

Миграции нет: откатить backend на предыдущий проверенный image/commit. Маршрут
restore снова станет недоступен; уже восстановленные записи остаются активными,
автоматически возвращать их в корзину нельзя. Если требуется отменить конкретное
восстановление, использовать существующее авторизованное удаление после проверки
текущей записи; это новое удаление с новой датой/автором, а не восстановление
старой записи корзины. Backup не восстанавливать поверх новых данных без сверки.

Независимый QA проверяет сценарии fixture, delete→deleted→restore и отсутствие
частичной записи при искусственной ошибке. Инструкция со скриншотами, CI и
релизное принятие остаются отдельными gates; NEED-001 не closed.
