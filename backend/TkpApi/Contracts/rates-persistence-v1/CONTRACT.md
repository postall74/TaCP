# RATE-001 — rates-persistence-v1

Основание: ADR-009, PM contract `c25dda1a5d860213ec5b5ddafe8a6e95c47b11bd`.
Production base: `1edff933afe9f488f11137ffa9251bae6744c720`.

## HTTP и совместимость

`GET /api/rates` — Staff, 200 с прежним Rates DTO.
`PUT /api/rates` — AdminOnly, 200 с полным принятым Rates DTO.
Поля: `design`, `production`, `software`, `smr`, `pnr`, JSON numbers / C# decimal.
Анонимный запрос — 401; недостаточная роль — 403; некорректный JSON/decimal —
400 от прежнего ASP.NET binding. Новых полей, прав, диапазонов или округления нет.
Примеры и ожидаемые результаты — [fixture.json](fixture.json).

PUT заменяет полный набор одним SQL UPDATE и возвращает ответ только после
успешной записи. Это не PATCH: пропущенные свойства сохраняют прежние defaults
DTO, включая PUT `{}`. При конкурентных запросах побеждает один целый DTO;
optimistic concurrency/version/409 не добавлены. Чтение не кэшируется между
запросами. Отсутствие обязательной строки — ошибка целостности БД (500), а не
скрытая подстановка defaults или успешный PUT без записи.

## Хранение и миграция

`20260929183448_PersistTenantRates` создаёт `rate_cards` с PK Id и CHECK Id = 1,
пятью unrestricted PostgreSQL numeric NOT NULL и одной строкой:
Design=1800, Production=1800, Software=2200, Smr=1800, Pnr=1800.
DTO Rates не является EF entity; отдельный RatesRow содержит внутренний Id.
Миграция не изменяет другие таблицы и данные. Таблица принадлежит той БД,
которую уже выбрал runtime tenant, без дополнительного tenant routing.

У исходной версии ставки существовали только в памяти процесса. Автоматически
извлечь их из старого DB dump невозможно. До остановки старого API администратор
сохраняет GET `/api/rates`, замораживает запись, делает backup БД. После миграции
перед открытием записи он возвращает сохранённый DTO через авторизованный PUT
и сверяет GET. Без этого существующая БД получает defaults, а не неизвестные
прежние ставки. Ставки старой версии, уже потерянные при рестарте, не восстановить
этой миграцией. Для новых БД defaults ожидаемы.

Обновление выполняется обычным запуском API (Database.Migrate). Для управляемого
окна миграции можно использовать `dotnet ef database update` с внешней
конфигурацией и явным выбранным tenant. До первого запуска проверить backup,
схему и `__EFMigrationsHistory` по TEN-001 runbook. Старый процесс необходимо
остановить: смешанные старые/new API писатели не поддерживаются.

Исправлен legacy baseline: если в БД уже есть таблицы, но нет applied migrations,
помечается только начальная `20260906110630_AddCabinetSegmentsPersistence`,
после чего новые миграции действительно выполняются. Прежнее поведение помечало
все миграции выполненными и пропустило бы создание rate_cards. Это не проверка
произвольной legacy-схемы: автоматическое признание начальной схемы осталось
старым ограничением. Не запускать на неизвестной/частичной схеме без preflight.
При уже существующей конфликтующей таблице rate_cards миграция остановится;
автоматического overwrite или удаления нет.

## Rollback

Предпочтителен rollback API image без удаления дополнительной таблицы, если
совместимость старой версии отдельно проверена. Старая версия опять хранит
ставки в памяти: до rollback экспортировать текущий DTO и закрыть запись,
после старта восстановить его прежним PUT. Новые изменения старого процесса не
синхронизируются с сохранённой таблицей: при повторном upgrade экспортировать
актуальный DTO и записать его в новый API до открытия трафика.

Down migration удаляет **только rate_cards**, теряя сохранённые ставки.
Применять её лишь после backup/export и остановки всех API выбранного tenant.
Для ревью SQL (настроить внешний runtime configuration, секреты не в команде):

```sh
dotnet ef migrations script 20260929183448_PersistTenantRates 20260906110630_AddCabinetSegmentsPersistence --project backend/TkpApi --output rates-down.sql
```

Проверить сгенерированный SQL и целевую БД перед применением. Повторный Up после
Down создаёт defaults; прежние значения возвращаются из сохранённого DTO.
БД другого tenant не останавливать и не изменять. Новых пользовательских данных
при восстановлении старого backup терять нельзя; действуют ограничения
[runbook TEN-001](../../Deployment/tenant-deploy-v1/MIGRATION_RUNBOOK.md).

## Передача QA и связь с NEED

QA проверяет defaults, PUT/GET, точность decimal, 401/403, restart, две разные БД,
миграцию существующей схемы с/без history, singleton и атомарность конкурентных
PUT. API restart проверяется отдельно от Docker volume/recreate gate OPS-001.

Прямого закрытия NEED-001…019 нет: RATE-001 обеспечивает хранение ставок и
частично поддерживает административные данные/расчёты. NEED-001 — только
косвенное partial; UI админпанели и статистика не реализованы этим diff.
Пользовательская инструкция со скриншотами, независимый QA, CI, merge и тег
здесь отсутствуют; ни одна NEED не объявляется closed.
