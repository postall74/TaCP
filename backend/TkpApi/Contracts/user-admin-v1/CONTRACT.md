# ADMIN-003 — user-admin-v1

Основание: ADR-012 / PM docs `24b7da66b73bdb342fb8d3bf34014ff01d8d34a8`.
NEED-001 partial; полный административный жизненный цикл не закрыт.

## API

`DELETE /api/auth/users/{id}` — AdminOnly, без тела запроса.

| Условие | Ответ | Изменения |
|---|---|---|
| Анонимный запрос | 401 | Нет |
| Manager/engineer | 403 | Нет |
| Неизвестный/уже удалённый ID | 404 | Нет |
| Удаление себя | 409 | Нет |
| Удаление последнего admin | 409 | Нет |
| Удаление другого пользователя, включая admin при наличии другого admin | 204, без тела | Identity-пользователь удалён |

Пустые 404/409 не вводят новый error DTO. Проверка self использует NameIdentifier
текущего JWT, проверка последнего admin — актуальные membership в БД. Маршрут не
заменяет JWT текущего администратора. Fixture: [fixture.json](fixture.json).

Удаляется только AspNetUsers и связанные Identity-записи по существующим FK
cascades (roles membership, claims, logins, tokens). Роли как справочник,
остальные пользователи, проекты, каталог и реквизиты не удаляются. OwnerId
проекта остаётся прежним строковым значением; передачи владения нет. Публичные
модели, существующие auth DTO и остальные маршруты не меняются. Миграций нет.

Существующие JWT проверяются прежним middleware по подписи/issuer/audience и
сроку; немедленного отзыва токенов при удалении этот срез не вводит. Удалённый
пользователь не может снова выполнить login, но ранее выданный JWT сохраняет
прежние свойства до истечения срока. Это особенно важно для QA last-admin:
обычно последний admin совпадает с текущим actor (self 409), отдельная ветка
last-admin достигается, например, прежним JWT другого уже удалённого admin.

## Транзакция и concurrent DELETE

До чтения target/membership берутся SHARE ROW EXCLUSIVE locks на AspNetUsers,
AspNetRoles и AspNetUserRoles в одной PostgreSQL-транзакции. Другие DELETE,
использующие этот маршрут, ждут освобождения и затем читают актуальное состояние.
Проверка наличия другого admin, удаление и commit составляют одну критическую
секцию; 204 возвращается только после commit. При A/B cross-delete один запрос
получает 204, другой 409; последний admin сохраняется. Это DB-lock, а не lock
памяти процесса, поэтому правило применимо к нескольким экземплярам API.

Ранние отказы не сохраняют изменений. Ошибка SaveChanges/commit откатывает все
Identity-изменения, включая cascades; не выдаётся ложный 204. Необработанная
ошибка БД возвращает стандартный 500. Короткая операция блокирует конкурентные
записи в три Identity-таблицы; длинные внешние транзакции могут увеличить ожидание.
Автоматический retry/deadlock handling и глобальное изменение auth не добавлены.

## Отдельный подтверждённый риск: PUT role

Существующий `PUT /api/auth/users/{id}/role` проверяет adminCount и
Rights.CanChangeRole вне транзакции, затем отдельно вызывает RemoveFromRolesAsync
и AddToRoleAsync. Его решение может устареть. Допустимое чередование по коду:

1. В БД два admin A/B. PUT роли A читает adminCount=2 и разрешает понижение A.
2. До записи PUT новый DELETE удаляет B: под lock он видит A и корректно оставляет
   одного admin на момент своего commit.
3. PUT продолжает с прежним решением и снимает admin с A. Admin не остаётся.

SELECT старого PUT не блокируется указанными table locks; даже если запись PUT
ждала DELETE, после освобождения lock старый PUT не повторяет проверку. Аналогичен
риск двух конкурентных PUT role. Это подтверждено анализом границ транзакций и
порядка операций; смешанный сценарий не исполнялся как runtime-тест.

Следовательно, гарантия текущего diff — concurrent DELETE между собой, а не
глобальный инвариант для всех auth-операций при смешанной конкуренции. PM уведомлён
до handoff и явно поручил не менять PUT в ADMIN-003. Исправление требует отдельной
задачи для общей транзакционной дисциплины смены ролей. Не заявлять этот риск
устранённым по успешному тесту DELETE↔DELETE.

## Rollback и QA

Откатить API на предыдущий проверенный image/commit: новой схемы нет. Ранее
удалённые пользователи автоматически не вернутся. Восстановление из backup требует
сверки новых данных; повторная регистрация создаёт новый ID и не восстанавливает
старые пароли, claims и связи. Не восстанавливать всю БД поверх новых записей
ради отмены одного удаления без отдельного решения.

QA проверяет матрицу fixture, concurrent DELETE, отсутствие изменений при
401/403/404/409, сохранность проектов и других пользователей, атомарность при
ошибке БД. Frontend scope — типизированный вызов, подтверждение и обновление списка
с сохранением JWT; здесь frontend не менялся. Независимый QA/CI и инструкция со
скриншотами остаются обязательными gates. NEED-001 не closed.
