# Заготовки задач для PM

Ниже — кандидаты для ROADMAP. PM должен присвоить окончательные ID, владельцев,
приоритет и принять ADR до перевода задач в `ready`.

## NORM-001 — принять normative-v1 и владельца обновлений

**Владелец:** PM + инженерный эксперт. **Зависит от:** ADR-004.

**Результат:** принят реестр применимых документов с редакцией, областью,
обязательностью, датой проверки, владельцем и политикой обновления.

**Критерии:**

- для каждого правила хранится документ, редакция, пункт, область и тип
  `mandatory|contractual|verification-method|guidance`;
- устаревшие 61439-1/-2-2013/2015 не используются для новых проектов после
  01.04.2026;
- изменение rule-set не меняет молча старые снимки проектов;
- юридическая/инженерная проверка обязательности оформлена отдельно от кода.

## CAB-001A — расширить cabinet-v1 исходными электрическими данными

**Владелец:** Backend. **Контракт:** `cabinet-v1`, новая версия при уже
опубликованной схеме. **Зависит от:** ADR-003, NORM-001.

**Результат:** шкаф содержит классификацию, габариты, условия среды, IP оболочки
и сборки, напряжения/токи, параметры КЗ, заземление, НКО, шины, способ установки
и ссылки на доказательства.

**Критерии:** DTO различает unknown/not-applicable/verified; сервер не принимает
противоречивые номиналы; старые записи мигрируют как `unknown`, а не получают
выдуманные defaults; опубликованы fixture и migration notes.

## NORM-002 — движок версионированных проверок

**Владелец:** Backend. **Контракт:** `normative-v1`. **Зависит от:** NORM-001,
CAB-001A.

**Результат:** проверка возвращает rule id, источник/пункт/редакцию, статус
`pass|fail|not-checked|not-applicable|needs-expert`, входные значения,
объяснение и доказательство.

**Критерии:** отсутствие входных данных никогда не превращается в `pass`;
смена редакции создает новый rule-set; снимок проекта сохраняет версию;
автоматические правила покрыты граничными и negative cases.

## WIZ-002 — классификация и исходные данные мастера

**Владелец:** Frontend. **Зависит от:** `normative-v1`, `cabinet-v1`.

**Результат:** до подбора пользователь выбирает тип изделия, объект, персонал,
среду, параметры сети и известные данные КЗ; мастер показывает пропущенные
исходные данные и область применимости подсказок.

**Критерии:** нельзя получить нормативный green-state без обязательных входов;
СП 256 не показывается для промышленной автоматики; редакция источника видна в
деталях; неизвестные значения сохраняются как неизвестные.

## ELEC-001 — защита, КЗ и координация аппаратов

**Владелец:** Backend + инженерный эксперт. **Зависит от:** CAB-001A.

**Результат:** модель и проверка ожидаемого КЗ, отключающей/токоограничивающей
способности аппаратов и заявленных `Icc/Icw/Ipk` НКУ.

**Критерии:** проверка использует точку установки и время защиты; при отсутствии
данных — `not-checked`; селективность/резервная защита не объявляются без таблиц
изготовителя либо расчета; QA имеет pass/fail/boundary fixtures.

## BUS-001 — расчет шин и одновременности

**Владелец:** Backend. **Зависит от:** ELEC-001, THERM-001.

**Результат:** явные `InA/Inc/Ing/RDF`, материал и геометрия шин, опоры,
тепловая и электродинамическая проверка.

**Критерии:** сумма номиналов автоматов не используется как расчет нагрузки;
эвристические диапазоны маркируются предварительными; результат содержит метод
и исходные данные; QA проверяет разные комбинации одновременности и КЗ.

## THERM-001 — доказуемый тепловой расчет

**Владелец:** Backend. **Зависит от:** CAB-001A.

**Результат:** расчет по ГОСТ 35224-2024 там, где метод применим, либо ссылка на
испытание/производную конструкцию; потери берутся из versioned каталога данных.

**Критерии:** категория оборудования не заменяет потери; проверяются условия
применимости метода; учитываются секции, ориентация, вентиляция и температура;
результат показывает температуры у компонентов и запас.

## IP-001 — IP оболочки и готового НКУ

**Владелец:** Backend/Frontend по опубликованному контракту.

**Результат:** отдельные IP пустой оболочки и сборки, состояние, вводы/вырезы и
доказательство.

**Критерии:** каталоговый IP не копируется как verified assembly IP; изменение
компоновки, вентиляции или вводов инвалидирует подтверждение; документ выводит
только подтвержденное значение либо явный статус.

## SEG-001 — корректная модель внутреннего разделения

**Владелец:** Backend, затем Frontend. **Зависит от:** CAB-001A.

**Результат:** форма выводится из размещения шин, функциональных блоков,
зажимов и барьеров по ГОСТ IEC 61439-2-2024.

**Критерии:** формы 2a/2b/3a/3b/4a/4b проверяются отдельными fixtures;
`partitions: 0..4` не служит доказательством; форма не приравнивается к
дугостойкости; инженер подтверждает предложенную форму.

## PE-001 — защитные цепи и заземление

**Владелец:** Backend. **Зависит от:** CAB-001A.

**Результат:** PE/PEN/N, защитные проводники, соединения съемных частей,
уравнивание потенциалов и протокол непрерывности.

**Критерии:** система заземления не сводится к количеству шин; валидируются
несовместимые схемы; приемо-сдаточный checklist содержит осмотр/измерение.

## EMC-001 — профиль ЭМС промышленного шкафа

**Владелец:** Backend + инженер по ЭМС. **Зависит от:** NORM-001.

**Результат:** версия электромагнитной среды, порты, разводка/экраны,
уравнивание потенциалов, УЗИП и план испытаний.

**Критерии:** УЗИП подбирается по оценке воздействия и параметрам интерфейса;
общие стандарты применяются только при отсутствии продуктового; `pass` требует
протокол или допустимый метод доказательства.

## SAFE-001 — функции безопасности и аварийный останов

**Владелец:** PM + инженер по функциональной безопасности; реализация после ADR.

**Результат:** отделены обычные функции управления и safety; хранятся ссылка на
анализ риска/SRS, безопасное состояние, требуемый SIL/PL и доказательство.

**Критерии:** мастер не назначает SIL/PL; количество кнопок не создает safety
function; обычный ПЛК не принимается как safety PLC; bypass/reset/диагностика
имеют явные требования и negative tests.

## DOC-001A — нормативная ведомость и протокол НКУ

**Владелец:** Frontend для preview, Backend для snapshot/PDF. **Зависит от:**
NORM-002 и профильных расчетов.

**Результат:** экспорт содержит применимые документы с редакциями, исходные
данные, результаты и ограничения; эскиз не называется ГОСТ-чертежом без
принятого стандарта оформления.

**Критерии:** PDF воспроизводим из snapshot; неизвестное не скрывается;
каждое заявление связано с rule/evidence; персональные/ценовые данные не
попадают в инженерный протокол без необходимости.

## QA-NORM-001 — матрица доказательств нормативных правил

**Владелец:** QA. **Зависит от:** NORM-002.

**Результат:** одна fixture-матрица применяется к TS/C# и документу.

**Критерии:** для каждого правила есть pass, fail, missing-input,
not-applicable и wrong-scope; проверены устаревшая редакция, смена rule-set и
сохранение старого snapshot; UI не показывает green-state при `not-checked`.
