# Инструкции для агентов ТКП·Про

Работайте от фактов в коде и от задач в `docs/ROADMAP.md`. Не используйте старые
описания в истории Git как спецификацию.

## Перед началом работы

1. При первом входе прочитайте `docs/TEAM_PROTOCOL.md`, `docs/ARCHITECTURE.md`
   и документ своей роли из `docs/agents/`. Затем читайте только изменения
   этих документов и материалы текущей задачи.
2. Возьмите одну задачу с идентификатором из `docs/ROADMAP.md`. Если у неё нет
   критериев приёмки или версии контракта, передайте её руководителю проекта, а
   не дополняйте требования догадками.
3. Работайте в отдельной ветке `codex/<роль>/<id>-<кратко>` и не меняйте чужие
   области владения.

## Границы владения

| Область | Владелец |
|---|---|
| `src/**`, кроме `*.test.ts` | Frontend |
| `backend/TkpApi/**`, кроме файлов тестов | Backend |
| `src/**/*.test.ts`, `backend/TkpApi.Tests/**`, CI и тестовые сценарии | QA |
| `docs/**`, план, решения, принятие задач | Руководитель проекта |

`src/types.ts`, `backend/TkpApi/Models.cs`, `src/api/client.ts`, миграции и
права — граница контракта. Менять их можно только в задаче с версией контракта и
с описанием обратной совместимости в `docs/ARCHITECTURE.md`. Владелец backend
публикует контракт; frontend и QA могут параллельно работать по зафиксированному
контракту и fixtures, не ожидая реализации API.

## Обязательные правила

- Только PM выполняет `git add`, `commit`, `push`, `merge`, `cherry-pick`,
  переписывание истории и публикацию PR. Frontend, Backend и QA редактируют
  свои файлы в отдельных ветках/worktrees и передают PM готовый diff.
  Ветки/worktrees могут создавать сами; чужие checkout не переключают.
- Handoff краткий: ID, worktree/ветка, base SHA, пути, проверки и ограничения.
  Перед коммитом PM автор подтверждает окончание записи; PM фиксирует только
  согласованные файлы и возвращает SHA для проверки. Секреты и артефакты исключены.
- Экономия контекста: адресный `rg`, ограниченные фрагменты и diff; без
  повторного чтения всего проекта, полных успешных логов и ответов «принял».
  Результат неизменного кода повторно проверяют только по новой причине.
- QA работает по событиям, без таймера: новый diff, исправление или падение CI.
  Проверяет изменённое поведение; к старому коду обращается при падении или
  установленной связи с дефектом. Обязательные CI/release gates сохраняются.

- Не добавляйте секреты, пароли, `bin/`, `obj/`, `dist/` или `node_modules` в Git.
- Не заявляйте о готовности без команд проверки из документа своей роли.
- Не редактируйте дорожную карту из feature-ветки: изменение приоритета, объёма
  или контракта передаётся руководителю проекта.
- При конфликте между документацией и кодом код описывается в `CURRENT_STATE.md`,
  а продуктовое решение фиксируется руководителем в `DECISIONS.md`.
